# Azure DevOps Pipelines

Source lives in GitHub; Azure DevOps is the sole CI/CD orchestrator. No GitHub Actions.

**Current state:** repository validation plus a guarded DEV topology/release path. The pipeline uses the self-hosted organization pool named `Default`; its agent must be online. A single agent executes jobs sequentially. Validation restores/builds/tests .NET, installs/builds/tests/lints the frontend, runs repository contract/feed checks, exercises local Docker dependencies, and compiles Bicep. In `pipelines/azure-pipelines.yml`, both `enableDevDelivery` and `enableCandidateFeed` currently default to `true`; queue with `enableDevDelivery=false` for validation-only runs. The release path captures an immutable image digest, validates VNet/subnets, publishes what-if and cost artifacts, and relies on configured approval/deployment checks. This repository cannot verify pool permissions, service connections, or server-side Environment approvals.

Validation jobs are defined independently, but a single online self-hosted agent runs them one at a time. NuGet, npm, and policy-Python package downloads use Azure Pipelines caches keyed to their lock/requirements files; the explicit `npm audit` gate is retained while `npm ci --no-audit` avoids running npm's implicit duplicate audit. The release image uses BuildKit with an explicitly created `docker-container` buildx driver and a mutable ACR `buildcache` tag for reusable build layers. The default Docker driver cannot export this registry cache, which otherwise fails the image job with “Cache export is not supported for the docker driver.” The deployed artifact remains the immutable image digest recorded in the release manifest. First runs populate caches and may not be faster. Cache hits and actual elapsed-time improvements must be measured from subsequent Azure DevOps runs.

The guarded DEV smoke verifies public health, PostgreSQL readiness/current schema, the application page, and fail-closed protected match routes. DEV disables local `X-Dev-*` authentication and configures the Entra issuer/audience; the smoke expects anonymous API requests to return `UNAUTHORIZED`. This verifies the API auth boundary, not an interactive browser sign-in journey. The SPA requests the exposed `api://<API-client-id>/Match.Read` scope, while the API validates the client ID GUID as its audience because the registration issues v2 access tokens.

## Setup
1. Connect private GitHub repo to Azure DevOps.
2. Create three separate Azure Resource Manager service connections using workload identity federation: an image publisher scoped to the exact ACR with `AcrPush`; a DEV app deployer scoped to `pm-dev-api-vnet`; and an infrastructure identity with custom, minimum actions for the selected subnet(s), Container Apps environment/app/job, PostgreSQL/Redis resources, private DNS, and an ACR-scoped `AcrPull` role assignment. This release also needs Container Apps job `read/write/start/action` and execution `read`, PostgreSQL database `read/write`, PostgreSQL Entra administrator `read/write/delete`, and managed-identity `read`. The pipeline rejects missing or reused connection names. Do not reuse the publisher identity or grant the infra identity broad `Contributor` at subscription scope. The infrastructure identity's what-if permissions and its write permissions must be reviewed separately; creating an ACR role assignment requires tightly scoped `Microsoft.Authorization/roleAssignments/write` at that ACR.
3. Configure Azure DevOps Environments `pitchmind-dev`, `pitchmind-stage`, `pitchmind-prod` with protected approvals and checks. Restrict pre-mutation pipeline queue/approval permissions and protected Environment approvers to the repository owner for each DEV change. The YAML `ManualValidation@0` pause alone is not owner-only: [Microsoft's task documentation](https://learn.microsoft.com/en-us/azure/devops/pipelines/tasks/reference/manual-validation-v0?view=azure-pipelines) says users with Queue builds permission can resume or reject it.
4. Register the Mac agent in the organization-level **Default** pool and keep it running. For interactive use, run `./run.sh` in the extracted agent directory; for background operation, install and start it with `./svc.sh install` and `./svc.sh start`. Confirm it appears **Online** under Organization settings → Agent pools → Default → Agents. The self-hosted machine needs Git, Docker Desktop with Compose/Buildx, Python 3, Azure CLI with Bicep, and sufficient free disk space. `UseDotNet@2` and `NodeTool@0` install the pipeline's .NET and Node versions.
5. Register `pipelines/azure-pipelines.yml` as the pipeline and authorize it to use the `Default` pool if Azure DevOps prompts for pool permission.
6. Set Azure Repos/GitHub PR branch protection to require this Azure Pipeline validation. This repository cannot verify that external branch policy from YAML; until configured and observed, required-check enforcement is unverified.
7. When queueing a validation-only run, explicitly set `enableDevDelivery` to `false`. The connection contract does not create service connections or authorize deployment. Verify actual queue and approval permissions, checks, and the online self-hosted agent in Azure DevOps.

The self-hosted agent is your Mac, not an Azure-hosted clean VM. Keep it powered on, awake, connected to the internet, and running to accept jobs. Pipeline code executes on that machine, so restrict who can queue pipelines and modify pipeline YAML. A single agent in `Default` means jobs queue rather than run concurrently. This avoids consuming Microsoft-hosted parallel-job minutes, but does not make Azure resources, network, or electricity free.

If the deployed DEV smoke reports `CERTIFICATE_VERIFY_FAILED` on this Mac, an outbound TLS inspection proxy is presenting a certificate chain that Python does not trust. Export the trusted proxy/root CA chain as PEM, then set `PITCHMIND_CA_BUNDLE` to that PEM file's absolute path on the agent. You can set it as an Azure DevOps pipeline variable, or in the agent service environment; restart the agent service only when you change its service environment. The smoke script uses this bundle while continuing to verify the server certificate; it does not disable TLS validation. Keep the CA file readable by the agent account.

## Private DEV topology parameters

- Queue `enableDevDelivery=false` until a release is intended. YAML defaults it to true, so the parameter must be checked on manual runs.
- Before using the opt-in path, have the subscription owner register `Microsoft.App`, `Microsoft.Network`, `Microsoft.ManagedIdentity`, `Microsoft.DBforPostgreSQL`, and `Microsoft.Cache` resource providers in the target subscription. The pipeline identity is not granted subscription-wide provider-registration rights.
- The target is the existing `pm-dev-vnet` in `rg-pitchmind-dev-001`. `container-apps` is a new, delegated ACA subnet; enter a free, non-overlapping IPv4 CIDR of `/27` or larger after checking every subnet. There is deliberately no default CIDR. The pipeline stops if it overlaps or uses the wrong VNet/subnets.
- The existing DEV PostgreSQL Flexible Server is `pitchmind-postgresql-dev` in `rg-pitchmind-dev-001`. When `provisionPostgres=false`, the guarded topology reuses it, creates the `pitchmind` database if missing, attaches a dedicated API managed identity, and runs an ACA migration job with a separate temporary Entra administrator identity. That job applies schema migrations and provisions the API's restricted `pitchmind_api` role; the deployment helper removes the migration identity's elevated PostgreSQL administrator mapping after successful completion. `provisionPostgres=true` remains an explicitly reviewed option for a new server.
- `provisionRedis=false` (default) selects the Redis Container App `pm-dev-redis-cache`; current DEV inventory reports image `redis:7-alpine` and one minimum replica. `provisionRedis=true` opts into the separate Azure Managed Redis deployment named `pm-dev-redis` and its private networking. Confirm actual regional SKU availability and cost before changing this option.
- The pipeline's what-if validator rejects deletes, out-of-group mutations, unexpected resource types, subnets, names, and role-assignment scopes. Review the exact published `private-dev-plan` artifact and estimated monthly cost at the second manual gate. `ManualValidation@0` alone is not owner identity enforcement; configure owner-only queue permissions and protected Environment approvers.
- The guarded topology declares PostgreSQL identity/grants and cache configuration. A successful template apply still does not prove private DNS, role mapping, database grants, or runtime connectivity. Check `/health/ready` and run the per-event verification chain documented in [M03](../docs/engineering/M03-AZURE-DEV.md).

Never place secrets in pipeline YAML. PRs must not receive production credentials.
