## HLD — system responsibility and architectural boundaries
**Workstream:** Football Analytics. **Owning components / intended files:** Domain tactical rules + Application mechanism use cases.  
**Architecture pattern:** deterministic detection + evidence graph.  
**Design task unique to this story:** Design staged detector: eligible trigger, spatial pressure, opponent response, controlled regain, transition, outcome; versioned policy.

- Honor separation: Domain pure football rules; Application use-case/ports; Infrastructure adapters; thin API; React presentation. Deviations require ADR/diagram update.
- Inputs must be synthetic, versioned, immutable and sourced through the canonical feed/ledger; no match-specific values hardcoded in C# or React. For infra/quality stories, source refs and environment/release artifacts are also versioned.
- Inputs and outputs carry `matchId, canonicalRevision, selectedTime/sequence` whenever football-related; evidence IDs/provenance where making claims. On errors return structured failure, never guess missing facts.
- Public contracts and security/role boundaries: Football LLD Sections D-G; details in [Azure HLD](../../../architecture/06-target-azure-hld.md), [Football LLD](../../../architecture/07-football-analytics-detailed-lld.md), [API](../../../api/API.md) and [Frontend](../../FRONTEND-SCREEN-CONTRACTS.md).
- Failure and scalability design: bounded memory/queue/retries, cancellation, idempotent effects and telemetry. PostgreSQL is source of truth; optional cache or AI failure cannot rewrite match state.

3. **Concrete engineering change:** Design staged detector: eligible trigger, spatial pressure, opponent response, controlled regain, transition, outcome; versioned policy.
4. **Data/persistence semantics:** No match facts in UI/source; mutate canonical event/projection/outbox only in ordered transactional scope if this story writes football state. 5. **API/consumer coupling:** Update `docs/api/API.md`, typed .NET/React schema fixtures and selected-time guarantees for any exposed route; reject incompatible fields, unsupported truth classifications and unauthorized users. No direct browser access to Azure secrets or Foundry.

7. **Negative/degraded cases:** include unavailable upstream data, malformed input, cancellation, auth denial, replay before evidence and at least one non-happy-path representative of this story.
8. **Environment:** LOCAL Docker or explicitly fake external port; DEV/STAGE/PROD Azure only, never locally emulated services in deployed configuration. No DEV changes before user approval.

## Local implementation evidence (2026-10-09)
The local offline implementation extracts a deterministic Domain detector under the fixed, versioned `press-sequence-v2` policy. The policy is structurally unapprovable in code (`unapproved-demo`, `publishable=false`) pending product/football review. It validates source-event ordering and selected-time prefix, uses declared fixture pitch dimensions and stadium-metre coordinates, requires frames at each distinct event time, and emits observed event/frame IDs plus conditions. The API exposes policy status and selected-time/source metadata; `canonicalRevision` remains null because this fixture is not a durable canonical projection. C4 and API docs describe this boundary.

Executed locally on 2026-10-09: `dotnet test PitchMind.slnx -c Release -m:1 --disable-build-servers` passed 64 tests across Application (13), Architecture (5), Contracts (16), and Domain (30); 15 PostgreSQL integration tests were skipped because no database prerequisite was configured. `frontend/npm ci --offline` installed the locked packages; `npm run build`, `npm test` (3 passed), and `npm run lint` passed. `node scripts/validate_operating_model.mjs` and `--self-test` passed; `git diff --check` passed. These tests cover selected-time exclusion, no tracking, successful circulation, unrelated regain, distant presser, non-synthetic provenance rejection, repeatability, API JSON properties, and architecture boundaries. When tracking is absent, tactical insight is suppressed and state projection fails explicitly with a tracking-required error. An independent read-only review confirmed the provenance guard and no-frame behavior and found no blocker to a draft PR; the reviewer did not rerun the tests. This does not satisfy the original acceptance gate: multiple Product-Owner-approved positives, football review of spatial/temporal thresholds, near-miss catalog, both teams/halves, and candidate-feed mapping/coordinate/metric validation remain outstanding. The detector is a local simulated candidate only; no canonical-feed/PostgreSQL integration or deployment is claimed.
