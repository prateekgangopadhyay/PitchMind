## Local implementation contract (EP04-S03)
The application port accepts one `CanonicalUpdate` created from `MatchAggregate` after applying the exact `MatchEvent`. The factory only snapshots the aggregate when that event is its most recently applied event, so callers cannot pass an arbitrary `MatchState`; a fabricated goal paired with the kickoff aggregate is rejected. The update carries a projection algorithm revision, algorithm version, lowercase source SHA-256, and immutable aggregate state immediately before the applied event. Under a per-match transaction advisory lock, `PostgresCanonicalUpdateStore` verifies that this predecessor matches the immediately preceding persisted projection by state hash, clock, sequence, source identity and provenance; the sequence-zero state must have the valid initial shape. This prevents an aggregate rebuilt from divergent history from appending a superficially contiguous event. The writer then assigns the next positive `canonical_revision` independently from the projection revision, and commits the event, projection state/hash and outbox payload carrying the same canonical revision. The event ID remains the stable outbox message ID. The writer holds an aggregate-owned mutation lease across preview, asynchronous persistence and in-memory apply; public `Apply`, preview and snapshot operations use the same gate, so another in-process caller cannot move the aggregate beyond the persisted event while the commit is pending. The PostgreSQL advisory lock remains the cross-process serialization boundary. Composite schema constraints tie admitted rows to the same match, canonical admission and projection revision. Exact retries return `AlreadyCommitted`; mismatched event/projection/outbox state rejects. An outbox insertion failure rolls back the event and projection.

`PostgresOutboxDispatcher` claims due rows with `FOR UPDATE SKIP LOCKED`, leases each claim, publishes with the stable ID, and records bounded exponential retries; exhausted messages are marked failed. It blocks a match’s later canonical revisions while any predecessor remains unpublished and not dead-lettered, so concurrent workers and retry delays cannot overtake that match’s earlier message. Publication is at-least-once: a process can lose the acknowledgement after a consumer commit and redeliver. `PostgresConsumerInbox.ExecuteOnceAsync` inserts the consumer/message receipt and runs a same-database effect in one transaction, so duplicate deliveries do not repeat that effect. This inbox guarantee applies only to effects performed on the same PostgreSQL transaction; remote side effects need their own idempotency contract. Schema v11 adds `IConsumerCheckpointStore`/`PostgresConsumerCheckpointStore`. A caller advances a partition cursor only after its inbox/effect transaction commits; updates preserve broker offset, broker sequence number, match/message identity and canonical sequence, reject gaps/backwards movement/conflicting duplicates, and are serialized per consumer partition. The old unused match-level cursor table is retained as `consumer_checkpoints_legacy_v10` without deriving broker offsets. The database cursor is separate from the Event Hubs SDK checkpoint call. The dispatcher emits `System.Diagnostics.Metrics` counters for publication/retry/dead-letter outcomes and a message-age histogram; no exporter, alert, or dashboard is wired yet. The store checks aggregate predecessor state against persisted projection history but does not yet rebuild the aggregate by replaying persisted football events; upstream aggregate construction must use canonical ordered history. No Event Hubs consumer invokes the checkpoint store or SDK checkpoint operation; no Service Bus adapter is wired.

| Failure point | Durable state | Recovery behavior |
| --- | --- | --- |
| Before canonical transaction commit | No event, projection, or outbox row | Caller may retry the same command. |
| Outbox insert fails after event/projection SQL | Transaction rolls back all three writes | Caller receives the database failure; no partial canonical update remains. |
| Commit succeeds before dispatch starts | Event, projection with canonical revision, and pending outbox row with the same revision | Any dispatcher can lease and publish the row. |
| Another in-process caller mutates or reads the aggregate during persistence | Aggregate mutation lease remains held by the writer | Direct aggregate mutation and snapshots wait until persistence and the writer's apply step complete; a competing append then sees the updated sequence. |
| Consumer commits but publisher acknowledgement is lost | Pending outbox row; consumer inbox receipt and effect committed | Retry may redeliver; inbox prevents repeating same-database effect. |
| Publisher repeatedly fails | Pending row with attempt and retry time, then failed state at limit | Alert/manual repair is required; no automatic poison replay is claimed. |

## Event Hubs projection consumer code slice — 2026-10-16

The Azure-only EventWorker now optionally registers `ProjectionConsumerWorker` when `ProjectionConsumer:Enabled=true` and the consumer group, consumer ID, Azure Blob service URI, and checkpoint container are configured. `EventHubProjectionEventHandler` validates the `ProjectionPublishedV1` body and broker properties before passing the original payload and typed snapshot to Infrastructure. `PostgresProjectionPublishedConsumer` verifies payload/state hashes and commits the message/payload receipt with the latest rebuildable snapshot in one PostgreSQL transaction. Duplicate same-ID/same-payload delivery does not repeat the effect; changed payload reuse, revision gaps, and conflicting equal revisions fail. Already-processed stale replay is recognized without moving the PostgreSQL cursor backward. Because `EventProcessorClient` invokes each partition callback sequentially in source order, the handler also advances the Azure Blob checkpoint after a safely deduplicated stale replay; this lets a lagging Blob checkpoint catch up during redelivery instead of replaying the same prefix on every restart. The caller advances the PostgreSQL partition cursor after effect commit, then advances the EventProcessorClient Azure Blob checkpoint; if the latter fails, redelivery is safe. The snapshot does not modify canonical event/projection tables. Schema v12 adds the consumer inbox and snapshot tables.

### Stale replay checkpoint recovery follow-up — 2026-10-16

Code commit `98b927c3` advances the EventProcessorClient Blob checkpoint after every successfully persisted or inbox-deduplicated event, including a stale PostgreSQL replay. This relies on the SDK's documented per-partition callback ordering and prevents a Blob checkpoint that trails the durable PostgreSQL cursor from replaying an already-processed prefix indefinitely across restarts. The PostgreSQL cursor remains protected from backward movement. At this code head, the EventWorker Release build passed with 0 warnings/errors and `EventHubOutboxPublisherTests` passed 21/21.
