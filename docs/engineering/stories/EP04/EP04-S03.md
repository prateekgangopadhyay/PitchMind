## Local implementation contract (EP04-S03)
The application port accepts one `CanonicalUpdate` created from `MatchAggregate` after applying the exact `MatchEvent`. The factory only snapshots the aggregate when that event is its most recently applied event, so callers cannot pass an arbitrary `MatchState`; a fabricated goal paired with the kickoff aggregate is rejected. The update carries a projection algorithm revision, algorithm version and lowercase source SHA-256. Under a per-match transaction advisory lock, `PostgresCanonicalUpdateStore` assigns the next positive `canonical_revision` independently from the projection revision, then commits the event, projection state/hash and outbox payload carrying the same canonical revision. The event ID remains the stable outbox message ID. Composite schema constraints tie admitted rows to the same match, canonical admission and projection revision. Exact retries return `AlreadyCommitted`; mismatched event/projection/outbox state rejects. An outbox insertion failure rolls back the event and projection.

`PostgresOutboxDispatcher` claims due rows with `FOR UPDATE SKIP LOCKED`, leases each claim, publishes with the stable ID, and records bounded exponential retries; exhausted messages are marked failed. It blocks a match’s later canonical revisions while any predecessor remains unpublished and not dead-lettered, so concurrent workers and retry delays cannot overtake that match’s earlier message. Publication is at-least-once: a process can lose the acknowledgement after a consumer commit and redeliver. `PostgresConsumerInbox.ExecuteOnceAsync` inserts the consumer/message receipt and runs a same-database effect in one transaction, so duplicate deliveries do not repeat that effect. This inbox guarantee applies only to effects performed on the same PostgreSQL transaction; remote side effects need their own idempotency contract. The dispatcher emits `System.Diagnostics.Metrics` counters for publication/retry/dead-letter outcomes and a message-age histogram; no exporter, alert, or dashboard is wired yet. The store accepts aggregate-derived state but does not yet rebuild the aggregate by replaying persisted football history; upstream aggregate construction must use canonical ordered history. Checkpoint table schema exists but this slice does not advance a consumer checkpoint. An Event Hubs/Service Bus adapter and EventWorker host registration are not part of this change.

| Failure point | Durable state | Recovery behavior |
| --- | --- | --- |
| Before canonical transaction commit | No event, projection, or outbox row | Caller may retry the same command. |
| Outbox insert fails after event/projection SQL | Transaction rolls back all three writes | Caller receives the database failure; no partial canonical update remains. |
| Commit succeeds before dispatch starts | Event, projection with canonical revision, and pending outbox row with the same revision | Any dispatcher can lease and publish the row. |
| LOCAL durable sink accepts a message but the dispatcher loses the acknowledgement | Delivery row is committed; canonical outbox remains pending with a retry time | Retry uses the stable message ID; the local sink treats the identical payload as an idempotent no-op before the dispatcher acknowledges it. A same-ID conflicting payload fails closed. |
| Consumer commits but publisher acknowledgement is lost | Pending outbox row; consumer inbox receipt and effect committed | Retry may redeliver; inbox prevents repeating same-database effect. |
| Publisher repeatedly fails | Pending row with attempt and retry time, then failed state at limit | Alert/manual repair is required; no automatic poison replay is claimed. |

## LOCAL dispatch follow-up

At code commit `952c356aeac80371b1729e00635c67dc2f0cf5d3`, `PitchMind.EventWorker` registers the PostgreSQL outbox dispatcher only when `Runtime:Profile=local` and `Outbox:Provider=postgres-local`. It requires an explicit PostgreSQL connection string and fails closed for other profiles/providers; there is no implicit publisher. The LOCAL publisher commits each message to `pitchmind_local.outbox_deliveries`, keyed by the stable message ID, and checks payload equality on duplicates. The dispatcher marks the outbox row published only after this durable sink returns. A background poller retries infrastructure failures without logging message bodies or connection strings.

### Explicit fresh-database LOCAL migration

The first PR revision did not apply the canonical schema from `dev-up`, and EventWorker never invokes migrations. The supported fresh LOCAL startup is therefore explicitly sequenced: `./scripts/dev-up.sh`, `./scripts/dev-migrate.py`, then `python3 scripts/dev-event-worker.py`. `PitchMind.DbMigrator` is a separate loopback-only executable requiring `Runtime:Profile=local`; the wrapper resolves the LOCAL Compose endpoint and invokes it with the database-owner identity. It applies the versioned PostgreSQL schema, then the owner refreshes grants for the separate `pitchmind_worker` login. EventWorker connects only as that restricted runtime role and never runs migrations. The worker may be started only after the migration command succeeds. The local schema bootstrap is plain SQL so the same table creation can run through Npgsql integration tests; psql-specific role/bootstrap commands live in a separate file.

This explicit local workflow does not add a cloud migration job or deployment. Production identity/grant design remains outstanding.

This adapter is a durable local handoff for exercising dispatch semantics; it is not Event Hubs or Service Bus. The API/use-case still does not invoke `PostgresCanonicalUpdateStore`, and this change does not admit or import `manu-liv-match-dataset.json`. Azure publisher registration, source-envelope replay, checkpoint advancement/rebuild, production runtime grants, metrics exporter/alerts, backup restore and cloud identity remain unimplemented or unverified. No cross-service exactly-once guarantee is made.
