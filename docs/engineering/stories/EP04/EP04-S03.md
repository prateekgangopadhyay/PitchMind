## Local implementation contract (EP04-S03)
The application port accepts one `CanonicalUpdate` created from `MatchAggregate` after applying the exact `MatchEvent`. The factory only snapshots the aggregate when that event is its most recently applied event, so callers cannot pass an arbitrary `MatchState`; a fabricated goal paired with the kickoff aggregate is rejected. The update also carries a strictly increasing projection revision, algorithm version, and lowercase source SHA-256. Before writing, `PostgresCanonicalUpdateStore` verifies that the source hash matches immutable metadata registered for the match; v3 foreign keys preserve that relationship after commit. It serializes writers with a per-match transaction advisory lock and commits the event, projection hash/state, and an outbox payload whose stable message ID is the event ID. A schema FK ties outbox rows to their projection revision. Exact retries return `AlreadyCommitted`; mismatched source/event/projection/outbox state rejects. An outbox insertion failure rolls back the event and projection.

`PostgresOutboxDispatcher` claims due rows with `FOR UPDATE SKIP LOCKED`, leases each claim, publishes with the stable ID, and records bounded exponential retries; exhausted messages are marked failed. Publication is at-least-once: a process can lose the acknowledgement after a consumer commit and redeliver. `PostgresConsumerInbox.ExecuteOnceAsync` inserts the consumer/message receipt and runs a same-database effect in one transaction, so duplicate deliveries do not repeat that effect. This inbox guarantee applies only to effects performed on the same PostgreSQL transaction; remote side effects need their own idempotency contract. The dispatcher emits `System.Diagnostics.Metrics` counters for publication/retry/dead-letter outcomes and a message-age histogram; no exporter, alert, or dashboard is wired yet. The store accepts aggregate-derived state but does not yet replay the persisted full football envelope itself; upstream aggregate construction must use the canonical ordered history. An Event Hubs/Service Bus adapter and EventWorker host registration are not part of this change.

| Failure point | Durable state | Recovery behavior |
| --- | --- | --- |
| Before canonical transaction commit | No event, projection, or outbox row | Caller may retry the same command. |
| Outbox insert fails after event/projection SQL | Transaction rolls back all three writes | Caller receives the database failure; no partial canonical update remains. |
| Commit succeeds before dispatch starts | Event, projection, and pending outbox row | Any dispatcher can lease and publish the row. |
| Consumer commits but publisher acknowledgement is lost | Pending outbox row; consumer inbox receipt and effect committed | Retry may redeliver; inbox prevents repeating same-database effect. |
| Publisher repeatedly fails | Pending row with attempt and retry time, then failed state at limit | Alert/manual repair is required; no automatic poison replay is claimed. |
