## HLD — system responsibility and architectural boundaries
**Workstream:** Canonical Persistence. **Owning components / intended files:** Domain + Infrastructure + transactional read models.  
**Architecture pattern:** canonical ledger + projection + outbox.  
**Design task unique to this story:** Migrate source metadata, tracking_frames, match_events, projections, insight_evidence, quarantine, checkpoint, outbox; strict role grants.

**LOCAL migration boundary:** `PitchMind.DbMigrator` is an explicit command, separate from API startup. It accepts only a loopback PostgreSQL endpoint, applies versioned schema migrations using the local owner credentials, then refreshes the `pitchmind_api` role. The API role can read canonical tables and the readiness schema version and can update only outbox lease/attempt/publication columns. It cannot execute DDL or mutate canonical events, projections, schema history, quarantine, or other outbox columns. Azure identity/migration delivery remains a separate cloud concern.

- Honor separation: Domain pure football rules; Application use-case/ports; Infrastructure adapters; thin API; React presentation. Deviations require ADR/diagram update.
- Inputs must be synthetic, versioned, immutable and sourced through the canonical feed/ledger; no match-specific values hardcoded in C# or React. For infra/quality stories, source refs and environment/release artifacts are also versioned.
- Inputs and outputs carry `matchId, canonicalRevision, selectedTime/sequence` whenever football-related; evidence IDs/provenance where making claims. On errors return structured failure, never guess missing facts.
- Public contracts and security/role boundaries: Football LLD Section H; details in [Azure HLD](../../../architecture/06-target-azure-hld.md), [Football LLD](../../../architecture/07-football-analytics-detailed-lld.md), [API](../../../api/API.md) and [Frontend](../../FRONTEND-SCREEN-CONTRACTS.md).
- Failure and scalability design: bounded memory/queue/retries, cancellation, idempotent effects and telemetry. PostgreSQL is source of truth; optional cache or AI failure cannot rewrite match state.

2. **Use-case and port:** Versioned migrations, canonical event ledger, match-state projections, algorithm/fixture/schema versions, evidence references and timestamp indexes, separate migration/runtime DB identities.
3. **Concrete engineering change:** Migrate source metadata, tracking_frames, match_events, projections, insight_evidence, quarantine, checkpoint, outbox; strict role grants.
4. **Data/persistence semantics:** No match facts in UI/source; mutate canonical event/projection/outbox only in ordered transactional scope if this story writes football state. Read models are revisioned; late corrections create new append-only revision. UI stories query and display, never persist canonical truth.
   - Admission `canonicalRevision` is a positive per-match PostgreSQL `BIGINT` assigned atomically by the canonical admission writer and shared by all events/frames admitted in that transaction. The existing integer `revision` on projections remains a projection/algorithm revision. Migration v3 adds the separate field and lineage constraints; legacy rows remain NULL until an explicit canonical admission/reconciliation process can establish provenance. The EP04-S02 read port selects by `(matchId, canonicalRevision, projectionRevision)` and returns both revisions; the database permits multiple projection revisions for one admission revision.
5. **API/consumer coupling:** Update `docs/api/API.md`, typed .NET/React schema fixtures and selected-time guarantees for any exposed route; reject incompatible fields, unsupported truth classifications and unauthorized users. No direct browser access to Azure secrets or Foundry.
6. **Observability:** correlation ID, source/fixture revision and algorithm version where relevant, sanitized structured event codes, duration/lag/retry outcome metrics; never log secrets or raw copyrighted feed.
7. **Negative/degraded cases:** include unavailable upstream data, malformed input, cancellation, auth denial, replay before evidence and at least one non-happy-path representative of this story.
8. **Environment:** LOCAL Docker or explicitly fake external port; DEV/STAGE/PROD Azure only, never locally emulated services in deployed configuration. No DEV changes before user approval.

## Focused migration compatibility evidence
- Local implementation on the EP04-S02 child branch makes the v4 provenance foreign key `NOT VALID`, which preserves existing projection rows during upgrade while PostgreSQL still enforces the constraint for new writes. Projection reads now join the immutable match source identity, so a legacy projection without a matching source record is not returned.
- Added a PostgreSQL regression that simulates schema v3 with both a NULL-revision legacy row and a valid-revision orphan projection, reapplies v4, confirms both rows remain and the positive-revision orphan is hidden by the read join, checks the new FK is unvalidated, and verifies a new orphan insert is rejected.
- Executed the Infrastructure PostgreSQL integration suite against an isolated database on the existing LOCAL Compose service: **8 passed, 0 failed, 0 skipped**. The temporary database was dropped after the run. `git diff --check` passed.
- This is focused migration/read-path evidence only. It does not prove least-privilege runtime grants, backup/restore, full ingestion or write-path provenance, deployment readiness, story acceptance, or PO approval. The story remains pending independent review and PO acceptance.

## LOCAL migration identity implementation — 2026-10-16

- Added `PitchMind.DbMigrator` and `scripts/dev-migrate.py` as an explicit local operation. The launcher resolves the Docker Compose PostgreSQL mapping, refuses non-loopback publication, and passes the owner connection and API password through process environment; neither credential is logged. The migrator requires `Runtime:Profile=local`, rechecks the loopback host, applies schema migrations, then provisions least-privilege grants.

## LOCAL API credential validation follow-up — 2026-10-16

The explicit migration launcher and PostgreSQL role provisioner now both enforce the bootstrap's minimum of 12 unique lowercase hexadecimal digits in the 48-character API password. This closes the bypass where a manually edited `.env` could pass format validation but use a low-diversity password when invoking the migrator directly. Re-provisioning also resets elevated role flags, role memberships, owned objects, and direct grants across non-system schemas before reapplying the intended runtime permissions. The PostgreSQL regression deliberately creates these elevated conditions and confirms the reset. The password format check uses absolute regex anchors and rejects a valid high-diversity value with a trailing newline before opening PostgreSQL; the focused regression covers both invalid forms. Exact test counts and isolation details are in [the credential and role reset evidence](../../evidence/EP04-S02-LOCAL-API-PASSWORD-GUARD-2026-10-16.md).
