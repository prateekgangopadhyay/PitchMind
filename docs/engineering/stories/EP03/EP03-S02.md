### Current v1 contract design
- Wire contracts live in `PitchMind.Contracts.Telemetry.V1`; they do not make the Domain depend on serialization or a provider. JSON Schemas are `schemas/telemetry/v1/event-envelope.schema.json` and `tracking-frame.schema.json`.
- `EventEnvelopeV1` and `TrackingFrameV1` represent admitted canonical records, not raw source ingress. Each requires a positive, monotonically increasing per-match `canonicalRevision` assigned by the PostgreSQL canonical-admission transaction, distinct from `schemaVersion`, source schema version and sequence. All records committed in the same admission transaction use the same per-match revision; a correction is a new append-only revision. Outbox publication occurs after that transaction and preserves the assigned revision. This story defines the transport contract; it does not implement the revision allocator, persistence schema or feed importer.
- Pre-admission source events/frames retain their source ID, source sequence, source version/hash and provenance, but have no canonical revision and cannot validate as either v1 canonical DTO. Do not put source candidates on the canonical telemetry channel or fill the field from `schemaVersion`/source version.
- Each canonical envelope carries a schema version, canonical match/event/frame identity and sequence, explicit period/elapsed time, and a `SourceReferenceV1` with original record ID, original sequence, source schema version, source SHA-256, optional UTC source timestamp and distinct provenance/rights-review status.
- Event and frame validation returns stable `{code,path,message}` failures for rejection/quarantine. Player-action event types require team/player identity; substitutions require two distinct participants while preserving participant direction as an unresolved source mapping. Identity strings are capped at 128 characters and source labels/outcomes/status text at 256 characters; source hashes and timestamps are bounded by their wire formats. Non-negative values represented by .NET `long` fields are bounded by `Int64.MaxValue` in the wire schemas. Values are rejected, never truncated, and adapters must enforce byte limits before deserialization. Schema strings reject whitespace-only values and UTC timestamps reject non-zero offsets. Optional event start/end coordinates and tracking positions require declared coordinate units, pitch dimensions, axis origin and per-team attack direction; a located event must include the direction of its team. Pitch dimensions are bounded to 90–120 m by 45–90 m, matching the existing fixture boundary; transforms never infer coordinate semantics and allow elapsed time beyond regulation.
- This v1 vocabulary is a contract vocabulary, not an approved mapping of candidate feed labels. The candidate manifest remains `candidate_not_canonical`; no importer or persistence write is introduced here. Source-specific clock, coordinate, event, team and player mappings remain blocked pending the reviewed manifest and domain/PO evidence.
- Tests use generic synthetic contract values. A normalized coordinate golden checks opposing directions and a half switch; it is not evidence that the candidate JSON uses those semantics.

## Local independent-review follow-up — 2026-10-13

Independent exact-head review of PR #71 restack `35fffbcfdbe8f383ac143ea840388d3d8c523554` identified three validator/schema gaps. The local fix at `695f65a2d5c9eb1ce8536cfb6c8064775fae8bf2` requires the event team's declared attack direction when an event has a location, bounds schema integers represented by .NET `long` to `Int64.MaxValue`, and rejects substitutions whose two participant IDs are the same. Regressions cover each finding, and API/contract documentation describes the behavior and JSON Schema cross-field limitation. A second review identified that JSON Schema numeric values could exceed .NET `decimal` deserialization limits; the current local follow-up bounds decimal wire values to `Decimal.MaxValue` and declares non-negative coordinate values, with schema-assertion coverage.
