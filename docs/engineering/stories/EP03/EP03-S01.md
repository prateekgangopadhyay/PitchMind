## HLD — system responsibility and architectural boundaries
**Workstream:** Feed & Streaming. **Owning components / intended files:** data/simulations/ + feed adapter + Event Hubs producer.
**Architecture pattern:** JSON → canonical envelope → broker.
**Design task unique to this story:** Profile actual JSON fixture, declare rights, 90-minute chronology, roster/card/subs/press counterexamples, hash/version.

- Honor separation: Domain pure football rules; Application use-case/ports; Infrastructure adapters; thin API; React presentation. Deviations require ADR/diagram update.
- Inputs must be synthetic, versioned, immutable and sourced through the canonical feed/ledger; no match-specific values hardcoded in C# or React. For infra/quality stories, source refs and environment/release artifacts are also versioned.
- Inputs and outputs carry `matchId, canonicalRevision, selectedTime/sequence` whenever football-related; evidence IDs/provenance where making claims. On errors return structured failure, never guess missing facts.
- Public contracts and security/role boundaries: Simulation Feed Contract; details in [Azure HLD](../../../architecture/06-target-azure-hld.md), [Football LLD](../../../architecture/07-football-analytics-detailed-lld.md), [API](../../../api/API.md) and [Frontend](../../FRONTEND-SCREEN-CONTRACTS.md).
- Failure and scalability design: bounded memory/queue/retries, cancellation, idempotent effects and telemetry. PostgreSQL is source of truth; optional cache or AI failure cannot rewrite match state.

## LLD — implementable tasks, contracts, state and failure design
1. **Source and schema:** identify exact input fields/source adapter and validate field presence/type/size/clock/coordinate and source hash; classify missing data explicitly. The candidate JSON is available, structurally profiled, and pinned by a `candidate_not_canonical` manifest with an offline structural/integrity validator. This validator reports raw numeric coordinate ranges only; coordinate units/orientation, clock semantics, player metric quality, football review and canonical mapping remain gates. It does not produce a normalized feed or write canonical data. Preserve original source event IDs, 1-based sequence and source clock fields through any later adapter.
2. **Use-case and port:** Fictional teams/players, formations/roles, score progression, periods, disciplinary/substitution scenarios, possession phases, at least one sustained pressing pattern and counterexamples; seed and fixture metadata; provenance marked `synthetic`.
3. **Concrete engineering change:** Profile actual JSON fixture, declare rights, 90-minute chronology, roster/card/subs/press counterexamples, hash/version.
4. **Data/persistence semantics:** No match facts in UI/source; mutate canonical event/projection/outbox only in ordered transactional scope if this story writes football state. Read models are revisioned; late corrections create new append-only revision. UI stories query and display, never persist canonical truth.
5. **API/consumer coupling:** Update `docs/api/API.md`, typed .NET/React schema fixtures and selected-time guarantees for any exposed route; reject incompatible fields, unsupported truth classifications and unauthorized users. No direct browser access to Azure secrets or Foundry.
6. **Observability:** correlation ID, source/fixture revision and algorithm version where relevant, sanitized structured event codes, duration/lag/retry outcome metrics; never log secrets or raw copyrighted feed.
7. **Negative/degraded cases:** include unavailable upstream data, malformed input, cancellation, auth denial, replay before evidence and at least one non-happy-path representative of this story.
8. **Environment:** LOCAL Docker or explicitly fake external port; DEV/STAGE/PROD Azure only, never locally emulated services in deployed configuration. No DEV changes before user approval.

## Implemented candidate-validation slice and remaining scope
The manifest-pinned Python validator is an offline source-integrity check only. It checks the pinned bytes/hash and structural event, identity, period, source clock, coordinate-number, frame, and player-metric field shape; reports raw coordinate ranges, counts, and repeatable source-order digests; and returns a blocked-for-canonicalization status. A separate [measured football-data audit](../../evidence/EP03-S01-FOOTBALL-DATA-QUALITY-AUDIT-2026-10-11.md) records aggregate coordinate and metric ranges, chronology, roster-frame counts, source score snapshots, and exact-name event vocabulary comparison. Neither audit infers player identity, canonical event type, coordinate units/orientation, metric meaning, football realism, score truth, or replay semantics. Neither feeds the application, production API, PostgreSQL, or Event Hubs. The public match API continues to return `503 MATCH_DATA_UNAVAILABLE` until a separately reviewed canonical PostgreSQL read path exists; the fictional deterministic fixture generator remains test-only. Executed evidence for the candidate-only slice is recorded in [EP03-S01 candidate validation evidence](../../evidence/EP03-S01-CANDIDATE-VALIDATION-2026-10-11.md). This slice does not meet the story's complete 90-minute fixture, football-rule review, or Product Owner acceptance criteria.
