## Current implementation evidence (local only)
- Both in-memory and PostgreSQL event stores classify payload conflicts, malformed events, occupied sequences, sequence gaps and backwards events with stable codes and a quarantine or reconciliation disposition. The disposition is advisory classification; this change does not persist a quarantine record or run a reconciliation worker.
- Exact duplicate checks include the timestamp offset as part of payload identity, so the same instant represented with a different offset is rejected as a payload conflict.
- **Current local lateness policy:** zero events may be admitted beyond the next expected per-match sequence. A gap or stale sequence is rejected with `HoldForReconciliation`; a late event is not automatically buffered or replayed. This is in-memory/PostgreSQL store behavior only. Durable quarantine, reconciliation, bounded retries, and late correction revisions are not implemented here.
- The PostgreSQL adapter also scans the existing ledger for its first missing sequence before admitting any new event. A legacy ledger containing sequences `0, 2` therefore holds both sequence `3` and late sequence `1` at expected sequence `1`; the adapter cannot extend a ledger that its read path would reject as noncontiguous. Operators must reconcile the ledger before writes resume.
- Migration V2 replaces the historical V1 event-type constraint (`0..7`) with the current enum range (`0..10`). V1 remains unchanged as an upgrade source, and the integration regression proves a V1 database rejects current values before V2 and accepts `Turnover`, `FullTime` and `Pressure` after migration.
- Candidate source sequence remains 1-based and is not wired to these canonical stores; the source-specific mapping/conversion remains blocked pending feed approval. Do not infer candidate event admission from the store tests.
