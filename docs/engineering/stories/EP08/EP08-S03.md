## HLD — system responsibility and architectural boundaries
**Workstream:** Grounded Agents. **Owning components / intended files:** Application evidence ports + AgentWorker + Foundry adapter.  
**Architecture pattern:** bounded role handoffs around one read-only evidence packet.
**Design task unique to this story:** Evidence Curator validates and preserves the selected-time packet; Football Narrator generates one untrusted Foundry candidate; Claim Verifier reuses EP08-S04 and gates output. The curator is deterministic and read-only, the narrator makes one bounded model call, and the verifier discards candidate-authored prose. No agent receives a canonical write tool.

- Honor separation: Domain pure football rules; Application use-case/ports; Infrastructure adapters; thin API; React presentation. Deviations require ADR/diagram update.
- Inputs must be synthetic, versioned, immutable and sourced through the canonical feed/ledger; no match-specific values hardcoded in C# or React. For infra/quality stories, source refs and environment/release artifacts are also versioned.
- Inputs and outputs carry `matchId, canonicalRevision, selectedTime/sequence` whenever football-related; evidence IDs/provenance where making claims. On errors return structured failure, never guess missing facts.
- Public contracts and security/role boundaries: Azure HLD / API / Football LLD; details in [Azure HLD](../../../architecture/06-target-azure-hld.md), [Football LLD](../../../architecture/07-football-analytics-detailed-lld.md), [API](../../../api/API.md) and [Frontend](../../FRONTEND-SCREEN-CONTRACTS.md).
- Failure and scalability design: bounded memory/queue/retries, cancellation, idempotent effects and telemetry. PostgreSQL is source of truth; optional cache or AI failure cannot rewrite match state.

## LLD — implementable tasks, contracts, state and failure design
1. **Source and schema:** consume `MatchIntelligenceContextBuildResult` from the authorized, selected-time EP08-S01 read-only tool. Validate match ID, canonical revision, projection time, sequence watermark, score, hashes, evidence type/identity/order bounds, clock, period, payload JSON, trust boundary, serialized size, and context policy version before any model call. The supplied Manchester United–Liverpool source file has confirmed synthetic provenance and redistribution permission; coordinate units, player metrics, football realism and canonical mapping still require validation. It is not read directly by this workflow.
   Match-time values remain source elapsed seconds; this internal path has no universal 90-minute ceiling and must preserve added-time values such as the candidate feed's 5,761 seconds. The offline demo API's separate 0..5400 fixture contract is not evidence that canonical events end at 90:00.
2. **Use-case and port:** `ExplanationAgentOrchestrator.GenerateAsync` accepts the read-only context result, audience, bounded question and cancellation token; the existing `IExplanationCandidateGenerator` is the Football Narrator port. An `ExplanationAgentTrace` records workflow ID/version, match/revision/selected time/through-sequence, three ordered roles, input/output evidence IDs, context fingerprint, duration, token usage where supplied, and safe failure code. It stores neither raw evidence payloads nor generated text.
3. **Concrete engineering change:** Implement the orchestrator as an internal AgentWorker workflow alongside the managed-identity Foundry adapter and EP08-S04 verifier. Evidence Curator performs deterministic validation without reordering or adding facts; Football Narrator makes at most one model call; Claim Verifier returns the only publishable type. Defer DI registration until a real `IMatchIntelligenceReadOnlyTool` implementation is composed. The Worker remains idle until an authenticated request/message consumer and context-tool composition are implemented; there is no public route or public result in this story.
4. **Data/persistence semantics:** No match facts in UI/source; mutate canonical event/projection/outbox only in ordered transactional scope if this story writes football state. Read models are revisioned; late corrections create new append-only revision. UI stories query and display, never persist canonical truth.
5. **API/consumer coupling:** No API contract changes: the workflow is an internal AgentWorker capability and is not exposed to HTTP/React. Update API documentation to state this boundary; reject incompatible context metadata, unsupported truth classifications and missing authorization failures before invoking the model. No direct browser access to Azure secrets or Foundry.
6. **Observability and budgets:** A maximum of three handoffs, one Foundry request, configured output-token cap, 32 KiB packet cap, 20-second workflow timeout, and four concurrent workflows by default. No retry is attempted. Record safe workflow ID, revision, selected time, stage durations, outcome, and provider-reported token counts; never log prompts, payloads, candidate text, secrets, or access tokens. These are configured caps, not a measured cost estimate.
7. **Negative/degraded cases:** include unavailable upstream data, malformed input, cancellation, auth denial, replay before evidence and at least one non-happy-path representative of this story.
8. **Environment:** LOCAL Docker or explicitly fake external port; DEV/STAGE/PROD Azure only, never locally emulated services in deployed configuration. No DEV changes before user approval.

## Verification plan — executable gate
- **Story-specific tests:** successful and failed role handoffs; selection/context/time/sequence rejection before Foundry; authorization-denied context; unavailable model, timeout and cancellation; malformed or out-of-packet candidate; verifier output contains no candidate prose; audience variants retain identical evidence IDs; one-call controlled single-agent baseline comparison on the same test candidate.
- **Regression scope:** .NET xUnit tests / PostgreSQL isolated integration for backend; frontend Vitest/Playwright/axe for UX; Bicep compile and read-only what-if for platform; red-team and semantic claim checks for AI.
- **Proof fields:** test command and runner, passed/failed/skipped counts, fixture SHA and version, Git commit/digest, API example/HTTP response, accessibility/screenshot evidence as appropriate, security/FinOps review, and owner signature.
- **Authoritative acceptance, unchanged:** Trace shows distinct roles, inputs/outputs and successful/failed handoffs; a single-agent baseline comparison shows the fail-closed verifier adds a measurable safety boundary with no additional model call. This deterministic test comparison does not establish real-model accuracy or audience preference; those remain unverified pending a governed evaluation dataset and review. A verifier-rejected claim is never returned as a fact.
- **Release decision:** verification and human PO acceptance required. Any cloud acceptance must use a separately approved change set; implementation or local tests are not DEV authorization.
