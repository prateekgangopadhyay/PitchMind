## HLD — system responsibility and architectural boundaries
**Workstream:** Optional Operations. **Owning components / intended files:** Infrastructure cache/jobs/exports.  
**Architecture pattern:** idempotent asynchronous operations.  
**Design task unique to this story:** Cache immutable snapshot by match/revision/time/rules version with TTL and rebuild; bypass on outage.

- Honor separation: Domain pure football rules; Application use-case/ports; Infrastructure adapters; thin API; React presentation. Deviations require ADR/diagram update.
- Inputs must be synthetic, versioned, immutable and sourced through the canonical feed/ledger; no match-specific values hardcoded in C# or React. For infra/quality stories, source refs and environment/release artifacts are also versioned.
- Inputs and outputs carry `matchId, canonicalRevision, selectedTime/sequence` whenever football-related; evidence IDs/provenance where making claims. On errors return structured failure, never guess missing facts.
- Public contracts and security/role boundaries: Azure HLD; details in [Azure HLD](../../../architecture/06-target-azure-hld.md), [Football LLD](../../../architecture/07-football-analytics-detailed-lld.md), [API](../../../api/API.md) and [Frontend](../../FRONTEND-SCREEN-CONTRACTS.md).
- Failure and scalability design: bounded memory/queue/retries, cancellation, idempotent effects and telemetry. PostgreSQL is source of truth; optional cache or AI failure cannot rewrite match state.

## Local implementation evidence — partial, not accepted
- Added an internal exact projection read keyed by `matchId`, `canonicalRevision`, selected elapsed seconds, and `algorithmVersion`; this is distinct from the existing projection `Revision`. PostgreSQL returns the canonical revision and the exact query constrains it and the reducer version.
- Preserved the existing non-cached point-in-time read path for legacy projection rows whose `canonical_revision` is NULL. The schema migration explicitly leaves this provenance unknown rather than inventing it; event-window verification now matches such rows with `IS NOT DISTINCT FROM`.
- Added a cache-aside boundary for immutable projection snapshots. The key format is `pitchmind:projection:v1:{matchId}:{canonicalRevision}:{selectedSeconds}:{algorithmVersion}`; TTL defaults to 30 seconds, serialized entries are capped at 1 MiB, and malformed/mismatched/hash-invalid entries are evicted best-effort before rebuilding from PostgreSQL. Cache read/write/removal failures fall back or remain non-fatal. Event-window reads are delegated directly to the canonical PostgreSQL reader.
- **Implementation gap:** `IMatchProjectionCache` is currently only a byte-store port. The current stable `StackExchange.Redis` 3.4.0 package was identified, but local restore failed with NU1301 because `api.nuget.org` DNS/network access is unavailable. Cached 2.7.27 and 2.8.16 were not used. No concrete Redis client adapter, configuration, DI registration, local Docker Redis integration, or Azure Managed Redis integration is implemented or verified.
- **Observed test evidence:** `dotnet test tests/PitchMind.Infrastructure.Tests/PitchMind.Infrastructure.Tests.csproj --no-restore -m:1 -p:BuildInParallel=false` — on 2026-10-11, **22 passed, 0 failed, 0 skipped** against a uniquely named temporary database created on the already-running local PostgreSQL service. This includes cache fake tests, exact-revision PostgreSQL tests, and the nullable-provenance regression case. The temporary database was dropped after execution; the existing `pitchmind` database and retained volumes were untouched. Restore used locally cached dependencies with `dotnet restore ... --ignore-failed-sources -p:NuGetAudit=false`; standard vulnerability audit could not reach NuGet.
- **Unverified gates:** real Redis flush/restart/corruption and outage behavior; Redis TTL/eviction/memory effectiveness; cache stampede/load; PostgreSQL exact-revision integration tests; Docker profile; Azure-only adapter/configuration; cloud cost; security review; independent technical review; named Product Owner acceptance; and deployment. No Azure resources were provisioned or changed.
