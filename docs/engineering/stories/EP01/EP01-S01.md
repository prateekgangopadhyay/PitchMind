# EP01-S01 — Enforce layered solution architecture

**Epic:** EP-01 | **Priority:** P0 | **Status:** Planned / requires independent proof | **Accountable role:** Principal Software Architect + Developer Experience Lead | **Dependencies:** baseline.  
**Canonical authority:** [Authoritative epic/stories](../../../backlog/HACKATHON-MVP-EPICS.md) and [Story execution register](../../../backlog/STORY-EXECUTION.md). This packet supplements rather than changes acceptance.

## Original user story
As a platform engineer, I need dependency boundaries that keep football rules deterministic and infrastructure-independent.

## Definition of Ready
- PO has confirmed football behavior, risk and source evidence (for non-football infra stories: operational user and target).
- The exact input/output contracts, match revision, auth and failure modes are versioned; source file rights are known.
- The concrete owner and independent reviewers are assigned (role in header is not a named person).
- baseline dependencies and test fixtures are available. No story is accepted because it appears in this document.

## HLD — system responsibility and architectural boundaries
**Workstream:** Platform Foundations. **Owning components / intended files:** C# / React / pipeline / local Docker.  
**Architecture pattern:** Clean Architecture / CI.  
**Design task unique to this story:** Define the supported .NET and React toolchain compatibility policy; reject domain dependency on Infrastructure/SDK by architecture tests; map every project to a C4 container.

- Honor separation: Domain pure football rules; Application use-case/ports; Infrastructure adapters; thin API; React presentation. Deviations require ADR/diagram update.
- Inputs must be synthetic, versioned, immutable and sourced through the canonical feed/ledger; no match-specific values hardcoded in C# or React. For infra/quality stories, source refs and environment/release artifacts are also versioned.
- Inputs and outputs carry `matchId, canonicalRevision, selectedTime/sequence` whenever football-related; evidence IDs/provenance where making claims. On errors return structured failure, never guess missing facts.
- Public contracts and security/role boundaries: EP01 / Azure HLD; details in [Azure HLD](../../../architecture/06-target-azure-hld.md), [Football LLD](../../../architecture/07-football-analytics-detailed-lld.md), [API](../../../api/API.md) and [Frontend](../../FRONTEND-SCREEN-CONTRACTS.md).
- Failure and scalability design: bounded memory/queue/retries, cancellation, idempotent effects and telemetry. PostgreSQL is source of truth; optional cache or AI failure cannot rewrite match state.

## LLD — implementable tasks, contracts, state and failure design
1. **Source and schema:** identify exact input fields/source adapter and validate field presence/type/size/clock/coordinate and source hash; classify missing data explicitly. `data/simulations/manu-liv-match-dataset.json` is now in main; canonical mapping, rights and football-quality certification remain open (see `docs/data/MANU-LIV-SOURCE-PROFILE.md`).
2. **Use-case and port:** Validate Domain → no external NuGet and no upward references; Application → Domain; Infrastructure → Application; API/workers → composition. Add explicit architecture tests for all projects and disallowed dependency directions.
3. **Concrete engineering change:** Define the supported .NET and React toolchain policy; reject domain dependency on Infrastructure/SDK by architecture tests; map every project to a C4 container.
   - `global.json` selects the .NET 10.0.1xx SDK baseline and allows the latest feature band for servicing. `.nvmrc` selects Node 22; `frontend/package.json` constrains Node 22 and npm 10–11; `package-lock.json` fixes the React and build-tool dependency graph. This is a compatibility/servicing policy, not bit-for-bit SDK/runtime pinning. Clean-machine reproducibility and setup are verified separately by EP01-S02.
4. **Data/persistence semantics:** No match facts in UI/source; mutate canonical event/projection/outbox only in ordered transactional scope if this story writes football state. Read models are revisioned; late corrections create new append-only revision. UI stories query and display, never persist canonical truth.
5. **API/consumer coupling:** Update `docs/api/API.md`, typed .NET/React schema fixtures and selected-time guarantees for any exposed route; reject incompatible fields, unsupported truth classifications and unauthorized users. No direct browser access to Azure secrets or Foundry.
6. **Observability:** correlation ID, source/fixture revision and algorithm version where relevant, sanitized structured event codes, duration/lag/retry outcome metrics; never log secrets or raw copyrighted feed.
7. **Negative/degraded cases:** include unavailable upstream data, malformed input, cancellation, auth denial, replay before evidence and at least one non-happy-path representative of this story.
8. **Environment:** LOCAL Docker or explicitly fake external port; DEV/STAGE/PROD Azure only, never locally emulated services in deployed configuration. No DEV changes before user approval.

## Follow-up: direct internal-reference guard — 2026-10-09

Independent reviews found that direct MSBuild `Reference` items, aliases with `HintPath`, imports, packages carrying internal assemblies, caller-set `IsImplicitlyDefined` metadata, relative alias paths, and references added by `BeforeTargets=ResolveReferences` or `BeforeTargets=ResolveProjectReferences` could bypass a literal `.csproj` scan or a broad framework exception. The architecture test now evaluates MSBuild items for each source project, executes `ResolveReferences` and `FindReferenceAssembliesForReferences` to inspect target-created assembly and project references, resolved `ReferencePath` and `ReferencePathWithRefAssemblies` compiler inputs, and target-added package/framework/COM/native references, checks full project-reference paths, resolves `HintPath` values relative to the owning project before inspecting assembly identities, and inspects package compile/runtime assets for `PitchMind.*` assemblies. Domain purity allows only the `Microsoft.NETCore.App` reference defined by the active SDK's exact `Microsoft.NET.Sdk.DefaultItems.props`; resolved and compiler references in Domain are rejected unless the assembly and any compiler reference assembly are verified non-PitchMind files under `Microsoft.NETCore.App.Ref` with an SDK-owned defining file. Negative fixtures reject forged implicit framework references, target-created framework/package references, out-of-map project references, an internal assembly added with the same Include as a baseline reference but a different HintPath, different target-item identities that share baseline metadata, direct external assemblies injected into Domain's resolved/compiler inputs, resolved-reference aliases carrying an internal assembly identity, and forged resolved-reference metadata that tries to disguise an Infrastructure binary as an allowed Application output or substitute its compiler reference assembly. Target-item deduplication now includes the MSBuild item identity (`Include`) as well as remaining metadata. SDK-generated assembly references are exempt only when they resolve under the .NET framework reference pack and their actual assembly identity is not PitchMind; SDK transitive project references are exempt only from the exact package dependency resolution target. Resolved internal assemblies are exempt only when their actual identity and exact project path match a project reachable through the documented dependency graph. Evaluation results are cached across test facts. Current local verification: a clean Release solution build passed with 0 warnings/errors; full Release suite passed 31 tests with 0 failures and 5 PostgreSQL integration tests skipped because no database prerequisite was available; focused architecture suite passed 13/13; Council validator and DAG self-test passed; `git diff --check` passed. Independent review found the target-item identity collision and Domain resolved-input gaps; follow-up review confirmed both fixes and found no remaining concern, but did not run the test suite. Human technical review and Product Owner acceptance remain outstanding. The follow-up below changes the runtime data boundary; C4, API and ADR-008 updates are recorded in the same PR.

## Follow-up: keep generated match data out of production — 2026-10-10

A fresh independent review found that `SyntheticFixtureGenerator` embedded fictional match events and tracking in `PitchMind.Domain`, and `SyntheticMatchService()` registered that data as the API default. This violated the HLD rule that match-specific values enter through a versioned source/feed. The generator now lives in the test-only `PitchMind.TestFixtures` project; the API no longer registers a default match service and ordinary match reads return structured `503 MATCH_DATA_UNAVAILABLE` until API route composition is replaced with a canonical, revisioned PostgreSQL-backed read port (the analyst route can return `429` when rate-limited before its handler). An architecture regression prevents the generator and named golden teams from reappearing under `src/`. The C4 Level 2/3 diagrams, API contract, local-development guidance and ADR-008 were updated in this change.

The production-fixture regression now scans both `src/` C# and `frontend/src/` JavaScript/TypeScript source. Test and spec files are excluded. The guard loads match, event, team, player and receiver identifiers from the candidate synthetic feed plus named test-only fixtures; focused negative cases prove it rejects a known golden team name in both C# and TSX and feed-derived event/team IDs in TSX. If the candidate feed is absent or not a JSON array, the guard fails rather than silently checking only the small static marker list.

The owner confirmed synthetic provenance and redistribution permission for `data/simulations/manu-liv-match-dataset.json`. A direct structural audit confirms 2,199 unique source event IDs with contiguous source sequence 1..2199. Canonical use remains blocked because source clock semantics, coordinate units/orientation, metric meanings and 19 event mappings are unverified; the shot/foul frequencies also need football Product Owner review. The source is not wired into the API, and no facts from it are currently served.

Exact-head follow-up on 2026-10-11: the architecture guard now derives its literal markers from event IDs, match IDs, team IDs/names, player names and receiver names in the approved candidate feed, including player-position identities. A regression reads a real event ID and team ID from that feed and proves the guard rejects both in production TSX. Focused feed-guard tests passed 3/3; full Release suite passed 37, failed 0, with 5 PostgreSQL integration tests skipped because no test connection was configured; architecture suite passed 19/19. The Council validator and `git diff --check` passed. The full test command built all solution projects successfully; a separate clean build was not rerun for this final test-only adjustment. Numeric match values and non-identity metadata are not scanned by this literal guard. Canonical feed review, independent review of the final head, human technical review and Product Owner acceptance remain pending; EP01-S01 stays unaccepted.

## Follow-up: candidate numeric alias used as a player shorthand — 2026-10-12

A focused architecture regression exposed a false negative: `const x = <candidate-feed-coordinate>; const frame = { playerPositions: [{ x }] };` was allowed because the numeric declaration was outside a recognized player record and `x` also names common layout geometry. The guard now detects the declaration when it is visible at an inline `playerPositions` array (or a named array variable) containing an `x` shorthand property. A negative case keeps the declaration unflagged when the player array uses an explicit, unrelated `x` value and the candidate alias is only used by layout shorthand.

The new positive case failed before the guard change and passed afterward.
