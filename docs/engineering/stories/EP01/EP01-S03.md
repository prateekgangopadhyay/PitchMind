## HLD — system responsibility and architectural boundaries
**Workstream:** Platform Foundations. **Owning components / intended files:** C# / React / pipeline / local Docker.  
**Architecture pattern:** Clean Architecture / CI.  
**Design task unique to this story:** Azure DevOps PR policy: dotnet, Node, Docker PostgreSQL tests, Bicep, SAST/SCA; no parallel GitHub Actions; publish TRX/JUnit.

- Honor separation: Domain pure football rules; Application use-case/ports; Infrastructure adapters; thin API; React presentation. Deviations require ADR/diagram update.
- Inputs must be synthetic, versioned, immutable and sourced through the canonical feed/ledger; no match-specific values hardcoded in C# or React. For infra/quality stories, source refs and environment/release artifacts are also versioned.
- Inputs and outputs carry `matchId, canonicalRevision, selectedTime/sequence` whenever football-related; evidence IDs/provenance where making claims. On errors return structured failure, never guess missing facts.
- Public contracts and security/role boundaries: EP01 / Azure HLD; details in [Azure HLD](../../../architecture/06-target-azure-hld.md), [Football LLD](../../../architecture/07-football-analytics-detailed-lld.md), [API](../../../api/API.md) and [Frontend](../../FRONTEND-SCREEN-CONTRACTS.md).
- Failure and scalability design: bounded memory/queue/retries, cancellation, idempotent effects and telemetry. PostgreSQL is source of truth; optional cache or AI failure cannot rewrite match state.

4. **Data/persistence semantics:** No match facts in UI/source; mutate canonical event/projection/outbox only in ordered transactional scope if this story writes football state. Read models are revisioned; late corrections create new append-only revision. UI stories query and display, never persist canonical truth.

7. **Negative/degraded cases:** include unavailable upstream data, malformed input, cancellation, auth denial, replay before evidence and at least one non-happy-path representative of this story.
8. **Environment:** LOCAL Docker or explicitly fake external port; DEV/STAGE/PROD Azure only, never locally emulated services in deployed configuration. No DEV changes before user approval.

## Verification plan — executable gate
- **Story-specific tests:** Deliberately failing test prevents merge; zero skipped PG suite.
- **Opt-in gate probe:** The Validate stage includes a dedicated `GateFailureProbe` job, disabled by default. A manually queued validation run with `runGateFailureProbe=true` sets `PITCHMIND_GATE_FAILURE_PROBE=1`; the dedicated xUnit test then fails, and its nonzero result must fail the stage. The repository validator checks that the probe remains opt-in, scoped to its test, and cannot ignore failure. Local execution proves test behavior and static pipeline shape only; a hosted Azure DevOps run is still required to prove the service executes the job and blocks the PR.
- **Regression scope:** .NET xUnit tests / PostgreSQL isolated integration for backend; frontend Vitest/Playwright/axe for UX; Bicep compile and read-only what-if for platform; red-team and semantic claim checks for AI.
- **Proof fields:** test command and runner, passed/failed/skipped counts, fixture SHA and version, Git commit/digest, API example/HTTP response, accessibility/screenshot evidence as appropriate, security/FinOps review, and owner signature.
- **Authoritative acceptance, unchanged:** An observed pipeline run provides green/failing checks on PR; a deliberately failing test blocks the gate; GitHub Actions is not introduced as a parallel CI owner.
- **Release decision:** verification and human PO acceptance required. Any cloud acceptance must use a separately approved change set; implementation or local tests are not DEV authorization.
