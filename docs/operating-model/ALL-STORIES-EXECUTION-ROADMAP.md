## Owners, parallelism and gates
Every story has exactly one **role-level accountable skill**, explicit consulted specialists and prerequisite stories in [machine-readable routing](STORY-EXECUTION-ROUTING.json). The `assignedHuman` field is null pending a real engineer or accountable operator assignment; a role skill cannot pretend to be a human employee or approve its own code. Avoid a blanket 28-role committee: engage only 1 DRI and relevant 2–4 reviewers. Use G0–G9 in [Operating Model](ENGINEERING-OPERATING-MODEL.md).

**Current to target critical path:** source JSON rights and unit manifest → canonical event/roster/frame admission → transactional PostgreSQL + outbox → football detector and evidence → selected-time API → seven-screen UX → validated Microsoft Foundry explanation → witnessed clean build/tests → explicitly approved Azure DEV deploy → hackathon demo. Independent lanes (UI shell, IaC preflight, backend mock contracts, threat model, goldens) can start before all preceding work finishes but cannot be accepted without the dependency contract.

## Source-specific blocking rules
The [source profile](../data/MANU-LIV-SOURCE-PROFILE.md) reports 2,199 match events, clock through 5761 seconds, 19 event types, 24 team/player identities, six goals and a 3–3 result. The feed has **no explicit top-level proof of synthetic provenance, coordinate units or distribution rights**. Unusually high event counts (124 shots / 254 fouls) and individual `heartRate`/stamina-like attributes require Product Owner, legal/privacy and football realism review. These numbers are *source observations* only. Do not map unitless 0–100 coordinates directly into metre-space rules. Do not put teams, scores, player names or events in C#/React. A raw JSON attachment is not authorization to publish a simulated real EPL feed.

## Integration protocol
1. DRI opens short-lived branch `feat/EPxx-Syy-description` from updated main; declare feature flag and changed contracts. **Do not merge this documentation PR by default**: preserve review and release approval gates.
2. Domain/data publish EventEnvelope and TrackingFrame schema with fixture SHA, source sequence/time/period/unknown units; consumer contracts first.
3. API commits no future-leak snapshot example, OpenAPI and typed test fixture; React uses network data and honest missing states, not literal mockup match stats.
4. Specialist reviewers sign only observed test artifacts, immutable code SHA and correct environment. Unverified, blocked or merely written remain unaccepted.
5. Architecture changes update C4 L1/L2/L3, deployment diagram, ADR, sequence, LLD, API and operational impact in the **same PR**.
6. Only **after** owner explicitly approves an exact story/change-set and Azure DevOps protected manual gate is satisfied may Azure DEV resources be mutated. PR merge, a pipeline parameter, existing DEV demo or earlier blanket permission is not adequate.
7. Progress must be written in the **existing** `docs/backlog/STORY-EXECUTION.md`; this routing registry is a work plan, not a second status authority.

Timebox the P0 demo path to Oct 27, 2026. Do not claim it is realistic to ship all P1/P2 enterprise capabilities in the remaining hackathon window without staffed capacity or actual signed evidence. P1/P2 remain in the execution graph for later completion.
