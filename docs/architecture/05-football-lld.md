# Football intelligence low-level design

Design supplement to the existing C4 HLD and ADRs, 2026-10-08. The **CURRENT** implementation boundary is stated below; other requirements describe **TARGET** behavior unless the execution register links passing evidence. For DEV, the runtime boundary is Azure-only; the Azure service flow is in the [Azure DEV HLD](06-target-azure-hld.md). No separate architecture supersedes C4.

## Current implementation boundary

The code contains deterministic domain/application logic for canonical event validation, replay, projections, evidence graphs and tactical candidates, plus PostgreSQL canonical readers. The DEV candidate path uses Azure Container Apps, Event Hubs, PostgreSQL candidate outbox/history, Blob checkpoints, a Redis Container App (`redis:7-alpine`), and Azure SignalR cursor notifications. This is the current resource inventory, not proof that every link is healthy; recent candidate analyst calls returned `503 ANALYST_UNAVAILABLE`. The candidate MANU–Liverpool stream persists raw records separately from canonical data and has not passed through canonical event mapping/admission. Canonical reads use the PostgreSQL BFF when configured readers and records exist; legacy fixture/demo endpoints remain fail-closed. The candidate analyst API can request a bounded hypothesis from a Foundry project agent; it is separate from canonical `MatchIntelligence`. The UI's tactical discussion helper is locally computed illustrative text, not a live agent discussion. See the [DEV integration status](../engineering/AZURE-DEV-LIVE-INTEGRATION-STATUS.md), [C4 Level 3](03-components.md), and [API registry](../api/API.md).

## Context and aggregate boundary

`MatchId` identifies the aggregate; `eventId` identifies an immutable input; sequence orders events within a match. Period and elapsed clock are separate from UTC occurrence/ingestion time. One query-selected elapsed timestamp drives scoreboard, events, pitch, evidence and analyst. Event kinds must distinguish an attempted shot from a goal. A goal updates score once; no xG or AI answer can update it. Active roster, dismissals, substitutions, side and period changes belong in the versioned reducer. Full competition rules, added-time offsets and corrected goals require explicit policy before implementation.

Canonical event admission validates match/team/player membership, finite bounded coordinates, clock bounds, period compatibility, source/provenance and supported schema. Stable IDs are derived from fixture version, seed, match and sequence, never from wall-clock time. Duplicate identical ID/payload is a no-op; conflicting duplicate is quarantined. Gaps pause strict canonical projection until reconciliation; late inputs produce a new revision with explicit correction semantics. No inferred coach intent, fatigue, strategy or injury is admitted as observed fact.

## Spatial convention

The canonical domain/test fixture uses stadium metres: x in [0,105], y in [0,68]; x is pitch length and y width. This is not an assertion about the DEV candidate JSON, whose coordinate units, axes, orientation, clock and player metric definitions remain unverified. The old repository normalized [0,100] convention is reference knowledge, not the new wire contract. Persist physical orientation and period, then derive a team-relative view that always attacks toward increasing x. Opponent positions in a frame must be transformed using the SAME selected viewpoint. Preserve raw coordinates and transformation version. Distances in the current detector use metre coordinates directly. Any future normalized display converts back to configured pitch metres before thresholds; normalized Euclidean units are not metres. Formation is nominal metadata until repeated phase-specific geometry supports a functional shape. Missing or stale tracking is reported and suppresses geometric conclusions.

## Governed pressing mechanism

The MVP candidate is an ordered press trigger → opponent response → exploitation → outcome chain. Minimum evidence is four distinct, match-local, same-period event IDs in nondecreasing clock and increasing sequence; pressure team and opposition are explicit; response belongs to the opposition; exploitation/outcome belong to the pressing team. Synthetic scenario labels cannot replace observable action/geometry evidence in a detector.

Versioned football policy must define eligible trigger actions, maximum window, possession transitions, team-relative zones, minimum coverage, exclusion reasons and threshold sensitivity. A back pass alone is not a press; a tackle count is not proof of coordinated pressure; a goal alone does not prove preceding pressure caused it. Temporal graph edges say `precedes`. Strong causal interpretation requires spatial/possession evidence and reviewed exclusions. Deterministic sequence candidates remain explicitly limited interpretations when this evidence is absent.

The test-only golden scenario for `press-sequence-v1` requires a completed goalkeeper back pass; opponent press-arrival frame; pressured incomplete pass within 10 seconds; same pressing team high regain within 10 seconds; then same-team cutback, shot and goal within 15 seconds of regain; all events occur in the same period and in strict time order. Its geometric test computes planar Euclidean distance in metres between the named pressing forward and goalkeeper at the press frame and requires ≤3 m. This is a deterministic test oracle, not an approved general football threshold or a production insight. Canonical routes can read persisted canonical projections, but the candidate MANU–Liverpool feed is not a qualified canonical input and does not drive this detector. Detection is suppressed if any referenced frame, participant, event outcome or threshold check fails. The rule does not establish intent or causal attribution. The golden includes extra tactical frames at event times because routine 30-second frames alone cannot support this temporal claim.

For expansion beyond the demo, split press detection into independently versioned phases: trigger eligibility, pressure exposure, opponent response, regain, exploitation and outcome. For each candidate publish a condition vector with observed values, policy threshold, missingness and provenance rather than one opaque confidence. Pressure exposure may later combine carrier-to-nearest-defender distance, defender closing speed projected on the carrier vector, approach angle, available outlets and local numerical balance. Compute speed only from sufficiently frequent timestamped frames; 30-second samples cannot estimate it. Do not infer body orientation from player centres. Label zone thresholds in metres and team-relative coordinates, and test mirror invariance when changing attacking direction. Report data coverage over the candidate window; low coverage suppresses spatial criteria rather than counting absent defenders as space.

Possession and territory are separate concepts. A regain requires an explicit controlled action or reviewed provider event, not merely nearest-player distance. A high regain requires the ball location transformed into the pressing team's attacking direction and a configured zone boundary. Track possession confidence/source and uncertainty; synthetic possession labels are fixture annotations. Candidate windows must not bridge halftime, substitutions that change active roster, or an unresolved sequence gap. Simultaneous events require stable sequence tie-breaks and must not be silently sorted only by wall-clock timestamps.

## Metric contracts and calibration gates

The present slice intentionally emits no xG, xT, pitch-control, expected-possession or calibrated player rating. When added, each metric needs a named outcome, observational unit, input schema, coordinate frame, algorithm/data version, coverage/missingness behavior, temporal scope and validation report. Keep descriptive counts separate from model estimates and tactical interpretations.

- **Shot xG:** estimate goal probability at shot time from shot location in metres, angle, body part, shot type, assist/cross context, defensive pressure and goalkeeper location only where those features are observed. Specify whether penalties, own goals, rebounds and blocked attempts are included. Train and test on rights-cleared representative data with season/team/time splits to limit leakage; assess calibration (reliability/Brier or log loss) and discrimination separately. A shot count or goal result is not a probability. If the synthetic fixture lacks features, return unavailable rather than fill from a generic table.
- **Expected threat (xT):** define a pitch grid in metres and a possession-action transition model over pass/carry states. Version the grid, success probabilities, shot values, source seasons and orientation transform. Evaluate held-out value calibration and compare with a simple location baseline. Do not copy an old table whose data provenance or licensing cannot be established. Deterministic replay must not use wall-clock time or mutable model defaults.
- **Pitch control / space:** only compute on sufficiently dense synchronized player/ball tracking with declared interpolation and tracking-quality bounds. Publish the model family, player arrival-time assumptions, velocity caps, uncertainty and team-relative transforms. Discrete synthetic centres or sparse sampled frames are not evidence of continuous control, off-ball runs or open passing lanes.
- **Pressing and possession:** count candidate sequences only after possession transitions and phase are resolved. Distinguish a trigger rate denominator (eligible opponent build-ups) from pressure duration, forced turnover, regain height and resulting shot. Stratify by match state and opponent build-up; compare with counterexamples and exposure time before describing effectiveness. A successful episode cannot establish a team tendency.
- **Player contribution:** attribute actions and effects to the involved player, not team outcomes alone. Avoid additive ratings that mix raw counts, xG, possession share and role without a declared normalization and uncertainty analysis. Goalkeeper, centre-back and forward roles need different opportunity denominators.

Every future metric test set should include invariance tests (mirror x/y transforms, identity relabeling, time replay), adversarial negatives (missing defenders, duplicate frames, clock reversal, extreme coordinates), slice analyses, reproducibility hashes and football-review signoff. Publish detector/model version and a concise evidence trace with each user-visible value. Threshold tuning belongs in a versioned policy change with golden fixtures and Product Owner/Football Analytics approval, never a silent runtime setting.

Positive goldens cover both teams/halves and a completed recovery/progression/shot chain. Negative goldens cover missing response, wrong-team progression, duplicate IDs, period boundaries, loss of possession, backwards clock, outcome beyond selected time and incomplete frames. Evidence includes ordered IDs, start/end, selected time, detector/fixture/schema versions, condition results and limitations. Confidence is never a fabricated probability; expose evidence completeness instead until calibrated.

## Persistence and asynchronous processing target

PostgreSQL tables: `matches`; append-only `match_events` with unique `(match_id,event_id)` and `(match_id,sequence)`; `tracking_frames`; versioned `match_projections`; immutable `insights`; `insight_evidence`; `quarantine`; `outbox`; `consumer_checkpoints`. Event plus projection/evidence/outbox intent commits in one transaction. Runtime may read/insert/update permitted tables; migrations use a separate identity. Cursor indexes begin with match ID and sequence or selected timestamp. Replay includes input, rules and transformation versions; output hashes exclude operational timestamps.

Outbox dispatch is at least once with stable message ID and idempotent consumer inbox. Failure uses bounded retries, observable poison state and a controlled replay path. Event Hubs partition key is match ID, but consumers still validate ordering. Service Bus carries commands; SignalR carries notification cursors and never durable truth. Reconnection obtains canonical backfill before resuming fan-out. Redis keys include match/revision/algorithm/selected-time and can be rebuilt.

## AI port and validation

Application composes a read-only `MatchIntelligence` snapshot at selected time with exact insight/evidence IDs, truth classes and limitations. Foundry receives this bounded context. Validate every candidate claim against known evidence, selected-time visibility, team/score and supported vocabulary before publication; substring or keyword matching alone is not sufficient. Invalid/timeout/unavailable candidates use deterministic evidence text. Audience changes style only. Budgets cover input length, calls, tokens, time and concurrency. Model deployment, authentication and cost limits are environment settings; no browser credential configuration.

The EP08-S02 adapter implements only candidate generation. It supports two HTTPS transports: Azure Foundry OpenAI-compatible chat-completions v1 using `ManagedIdentityCredential` with the Cognitive Services scope, or a Foundry project agent's OpenAI Responses endpoint using the project endpoint, configured agent name, and `https://ai.azure.com/.default` scope. Project-agent mode requires `Foundry:Mode=ProjectAgent`, `Foundry:Endpoint=https://<resource>.services.ai.azure.com/api/projects/<project>`, and `Foundry:AgentName` (defaults to `TacticalAnalyst`); model mode continues to require `Foundry:Deployment`. Both modes enforce Azure AI host suffix allowlisting, disabled HTTP redirects, bounded request/response sizes, 1–60 second timeout, 1–32 concurrent calls with immediate saturation refusal, output-token cap, strict candidate JSON shape, exact packet evidence-ID membership, and non-content success/failure telemetry. The versioned catalog has nine specialist lenses plus the evidence-first default, with phase-specific playbooks and profile-filtered retrieval of up to three knowledge cards. Returned candidates retain match/canonical revision/projection revision/selected-time/sequence and source/state lineage from the input packet. Membership checks are not semantic claim verification; EP08-S04 remains an independent gate. No Foundry resource, remote agent, model deployment, live model call, authenticated host composition, or production publication path has been verified. Project-agent mode does not create or mutate agents.

EP08 tactical knowledge retrieval is a distinct read-only advisory input to the Foundry adapter. `ITacticalKnowledgeRetriever` chooses up to three passages within the selected profile's topic allowlist. Development uses bounded local lexical ranking over embedded cards. Model-deployment Azure mode requires Azure AI Search `2025-09-01`, managed identity with the Search data-reader scope, a profile `search.in` filter, vectorizer-backed text-vector retrieval and semantic ranking. Project-agent mode can use the embedded curated cards when Search is not configured, while the remote Foundry agent can separately use its attached File Search resource; supplying all three Search settings selects the Azure AI Search adapter, and partial configuration fails startup. The index corpus is versioned curated cards and reviewed catalogue abstracts/URLs, not full third-party article text. Search service/index, vectorizer, role assignment, Foundry File Search attachment, and live retrieval are not verified. Knowledge passages cannot add canonical evidence IDs; match claims remain bound to the selected-time packet and verifier.

EP08-S03 adds `ExplanationAgentOrchestrator` as bounded library code in AgentWorker: an already-authorized read-only context tool is validated and fingerprinted, a single candidate generator receives that exact packet plus audience/question and a token cap, and `ExplanationCandidateVerifier` determines the only result that may be returned. Immediate concurrency refusal, linked caller/workflow cancellation, packet/evidence limits and role status traces bound the workflow. Traces contain no raw packet/model text; context IDs are recorded only after packet validation, candidate citation IDs are never traced, and only verifier-approved IDs are output. A test compares the unverified single-generator candidate with the verifier-gated result; this establishes the value of the deterministic publication gate, not a measured accuracy advantage for multiple model agents. The class is not registered or invoked by the Worker, uses the current 0..5400 selected-time request contract, and has no live Foundry, authenticated host-composition, cost/latency evaluation or product acceptance evidence.
