# Canonical telemetry contracts v1 (EP03-S02)

`schemas/telemetry/v1/` and `PitchMind.Contracts.Telemetry.V1` define version 1 of the transport-neutral **canonical** event envelope and tracking frame. Both require `schemaVersion` and `canonicalRevision`; these fields have separate meanings. `schemaVersion` selects the wire contract shape and is `1` here. `canonicalRevision` is a positive, monotonically increasing per-match revision assigned by the PostgreSQL canonical-admission transaction to the immutable event/frame at commit. Every item in the same admitted transaction carries that revision; a later correction is admitted under a new revision and does not rewrite the prior record. Unsupported schema versions fail with `UNSUPPORTED_SCHEMA_VERSION`; consumers must add an explicit version adapter before accepting a newer schema.

These contracts begin **after** source mapping and canonical admission. Raw/pre-admission feed events and frames have no `canonicalRevision`; they remain source candidates with source IDs, source sequence and provenance. They are not valid `EventEnvelopeV1` or `TrackingFrameV1` values and must not be put on the canonical telemetry channel. Missing revision fails deserialization/schema validation; zero or a negative revision fails runtime validation with `INVALID_CANONICAL_REVISION`. The target is for PostgreSQL to assign the revision atomically with canonical admission and the outbox to publish only the admitted envelope. This story defines that contract; it does not implement the revision allocator, persistence schema or feed importer. Until those exist, no source candidate is a valid canonical envelope. Source version/hash remain in `SourceReferenceV1` and must never be copied into `canonicalRevision`.

Canonical telemetry string bounds are fail-closed and never truncate identity or provenance: identity fields (match/event/frame/team/player and source IDs) are at most 128 Unicode characters; source labels, outcome text, schema labels, and provenance/review status are at most 256 characters; a source SHA-256 is exactly 64 lowercase hexadecimal characters; and a source timestamp string is at most 64 characters. JSON Schemas declare these wire limits, and the runtime validator enforces the corresponding bounds on string-valued fields after deserialization. `sourceTimestampUtc` is deserialized as `DateTimeOffset` and runtime validation requires UTC offset zero. Transport adapters must enforce a byte-size limit before JSON deserialization; string bounds do not replace payload-size controls. Overlong source values are rejected for quarantine/review rather than normalized or truncated.

All non-negative integer fields represented by .NET `long` (`sequence`, `matchTime.elapsedSeconds`, and `source.sourceSequence`) are bounded by `Int64.MaxValue` in the schemas so a schema-valid value can be deserialized by the runtime contract. Non-negative decimal wire fields use a 29-branch `anyOf`: each branch pairs an exact `multipleOf` from 1 through 10^-28 with the maximum coefficient .NET `decimal` can represent at that scale. Together, those branches reject values that fall below decimal scale or exceed the 96-bit decimal coefficient, including numbers that are below `Decimal.MaxValue` but still cannot be represented at their fractional scale. Pitch coordinates use the same reusable rule, while unit-specific coordinate ranges remain enforced by runtime validation; pitch dimensions combine it with their football bounds. A substitution's `playerId` and `relatedPlayerId` must identify different participants. JSON Schema draft 2020-12 cannot compare sibling property values, so the runtime validator enforces that cross-field rule and the schema documents the additional requirement.

## Event envelope

An event has a canonical `matchId`, positive store-assigned `canonicalRevision`, stable `eventId`, zero-based contiguous canonical `sequence`, explicit match time, known event type, the unmodified `sourceEventType`, optional team/player/related-player/outcome fields, and a required source reference. `canonicalRevision` identifies the immutable per-match revision that admitted this event; it is not the source revision, current head at read time, sequence or schema version. A response assembled at a later selected revision carries that selected revision at the response/snapshot level. Player actions require both `teamId` and `playerId`; period markers and kickoff can be playerless. A substitution requires both `playerId` and `relatedPlayerId` to retain the two participant identities without guessing a direction such as outgoing or incoming. Supplied optional text fields must contain a non-whitespace character. `SourceReferenceV1` retains the original source match/record IDs, source sequence, source schema version, source artifact SHA-256, optional UTC-offset-zero source timestamp, provenance status, and independent rights-review status. Canonical sequence conversion never overwrites source sequence or identity.

An event may include a start point, an end point, or both. When either is present, `coordinateSystem` is required and declares the pitch dimensions, source unit, axis origin and team directions. If the event has a `teamId`, that team's attacking direction must be present. The unused endpoint can be omitted or `null`; at least one endpoint must be a point. The same bounds and normalization rules used for tracking frames apply; the contract rejects points outside the declared pitch and pitch dimensions outside 90–120 m by 45–90 m. Events without locations do not need a coordinate system.

Match time has an explicit period, non-negative elapsed seconds, and the original numeric clock value plus unit and basis. There is no hard-coded 90-minute or 5,400-second ceiling. When the source basis is `match_elapsed` and the unit is `seconds` or `milliseconds`, validation requires the source clock to equal canonical elapsed seconds after exact conversion; inconsistent values fail with `SOURCE_MATCH_TIME_MISMATCH`. `period_elapsed` values cannot be reconciled to match elapsed time without an approved period offset, so that calculation belongs to the reviewed mapper. `provider_defined` values are retained without a unit conversion and do not independently verify canonical elapsed time. A source adapter must not calculate elapsed time from provider clocks until that provider's clock semantics are declared and tested.

## Tracking frame and coordinates

A frame has stable match/frame identity, positive store-assigned canonical revision, canonical sequence/time, ball and player points, source reference, pitch length/width in metres (90–120 m by 45–90 m), declared point unit (`metres`, `normalized_0_1`, or `percent_0_100`), declared axis origin, and explicit attacking direction for each player team. Validation rejects missing/non-positive canonical revisions, unsupported/missing units, out-of-range positions, duplicate players, missing/duplicate/invalid team directions, out-of-range pitch dimensions and unsupported schema versions with stable error codes and field paths. Coordinate normalization first converts to bottom-left-origin stadium metres; `ToAttackingXMetres` then uses the declared team direction. The transform is deterministic and does not infer source units or orientation.

## Candidate-feed boundary

The owner-confirmed JSON is still marked `candidate_not_canonical`. Its current manifest leaves coordinate unit/orientation, player metrics, canonical mappings, independent rights/privacy review, and football realism unapproved. This contract does not map any provider event label to a canonical type, approve candidate coordinates, present metric-like fields as player facts, or write data to PostgreSQL. A source-specific adapter remains blocked until those decisions are evidenced. The v1 vocabulary is a contract vocabulary only, not approval of all candidate source semantics.

## Evolution and failure handling

The JSON Schemas are the language-neutral wire definitions and constrain required strings against the same explicit Unicode whitespace set used by .NET `string.IsNullOrWhiteSpace`, .NET `long` integer values, exactly representable non-negative .NET `decimal` numbers, and timestamp offsets against non-zero UTC offsets. Runtime validation returns a list of `{code,path,message}` errors for deterministic rejection/quarantine; it performs cross-field checks such as match-elapsed clock consistency, distinct substitution participants, event-team direction coverage, coordinate ranges and duplicate players. Schema tests parse both JSON documents, assert the declared rules, and exercise the whitespace pattern with the .NET ECMAScript regex engine; they do not run a general JSON Schema engine. Per-record validators do not enforce cross-record contiguous sequence or same-revision batch invariants; canonical admission must enforce those transaction-level rules. The required revision field is part of the current v1 contract; consumers generated from earlier drafts must rebase/regenerate before using it. After v1 acceptance, any further breaking meaning or shape change requires a new schema version and compatibility adapter. Raw source lineage, event ID, source sequence, source clock, and source hash remain attached when normalized values are created.

## Verification

`tests/PitchMind.Contracts.Tests/TelemetryContractTests.cs` covers serialization identity/revision, missing and non-positive canonical revisions, schema incompatibility, unknown event type, invalid period, required, whitespace-only and overlong values, non-zero timestamp offsets, incomplete or duplicate-participant substitutions, schema declaration checks including .NET `long` and exact decimal representability boundaries, one-sided event-coordinate serialization, event-team and tracking-team direction validation, pitch bounds, invalid position/unit/direction, and explicit left/right second-half transforms. These tests use generic contract values and do not certify the Manchester United–Liverpool candidate feed.
