# ADR-002 — Messaging and reliable publication
Status: Accepted design; local PostgreSQL primitives and Azure Event Hubs publisher/consumer code are implemented. Azure runtime and cloud verification remain pending.

**Decision:** PostgreSQL is the canonical admission boundary. It assigns a positive per-match `canonicalRevision` and commits canonical changes plus outbox rows in the same transaction. Only the outbox dispatcher publishes admitted canonical telemetry to Event Hubs, partitioned by matchId and carrying the assigned revision. Raw source candidates do not use the canonical envelope or telemetry channel. Service Bus transports durable background commands (explanation, recap, exports, recovery). The dispatcher publishes idempotently with stable message IDs.

**Consequences:** At-least-once delivery is expected. Consumers deduplicate using stable message IDs, bound retries and isolate poison messages. EP04-S03 adds a PostgreSQL transaction port that binds aggregate updates to the persisted predecessor projection and immutable source identity, an aggregate-owned in-process mutation lease across preview/persist/apply, leased dispatcher state with renewal during active publish, a same-database inbox transaction, and local .NET metrics instruments. The Azure-only EventWorker leases PostgreSQL outbox rows, validates the shared `ProjectionPublishedV1` envelope and publishes its original JSON to Event Hubs with the stable outbox ID and `matchId` partition key using managed identity. Its optional EventProcessorClient consumer validates broker metadata against the envelope and passes raw payload plus a rebuildable projection snapshot to Infrastructure. One PostgreSQL transaction binds the stable message ID to the exact payload hash and applies the latest snapshot; replay with the same ID/payload is a no-op, conflicting payload reuse and revision gaps fail. After that effect commits, the worker advances the PostgreSQL partition cursor and then the Azure Blob SDK checkpoint. Invalid envelopes or projection conflicts are recorded in a bounded-metadata poison table before both cursors advance; raw bytes are not persisted. Poison rows stay `pending`; replay tooling and an Azure Blob checkpoint reset procedure are not implemented or verified in this slice. A corrected replay at the same broker position replaces the poison cursor and marks the row `replayed`; repeated delivery of the old invalid event will not move the cursor backwards. Stale already-processed deliveries do not move the cursor backwards. These steps are sequential across PostgreSQL and Blob Storage, not a cross-service transaction; redelivery remains safe through inbox idempotency. The consumer is opt-in and requires an Azure Event Hubs consumer group plus Blob checkpoint configuration. Schema v11 stores the broker cursor; schema v12 adds the payload-bound consumer inbox and rebuildable latest-snapshot table; schema v13 adds poison tracking and poison-aware cursor positions. The worker uses managed identity and verified TLS for Azure PostgreSQL; password-based connection strings are rejected. No Azure host, resource, live connection, hosted CI, Service Bus adapter, metrics exporter, or cloud runtime has been verified. Cross-service exactly-once delivery is not claimed.
