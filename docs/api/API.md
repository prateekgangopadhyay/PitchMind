# PitchMind — Consolidated API Contract and Implementation Registry
**Current baseline:** fail-closed fixture/demo routes with EP01-S04 typed contracts and a guarded LOCAL runtime profile. EP06-S01 adds a separate PostgreSQL-backed canonical BFF route family; EP06-S04 protects canonical and legacy match route families with role policies and abuse controls. Azure requires explicit Entra authority/audience but uses unavailable canonical readers until an Azure PostgreSQL adapter is configured. This worktree is not Product Owner accepted, and Azure identity/data integration remain unverified. Source files: `src/PitchMind.Api/Program.cs`, `src/PitchMind.Api/CanonicalMatchEndpoints.cs`, `src/PitchMind.Api/ApiSecurity.cs`, `src/PitchMind.Contracts/V1/MatchContracts.cs`, `frontend/src/api.ts`. No missing API is assumed working because it appears here.

## Principles
Public route prefix `/api/v1`; JSON camelCase; timestamps match selected-time contract, period/added-time explicit when supported; football data exclusively from versioned synthetic JSON/authoritative projections; `X-Correlation-ID` returned in every response. All read responses include `provenance`, `sourceVersion/hash`, `canonicalRevision`, `schemaVersion` and `asOf` **once implemented**. Never leak events later than `atSeconds`. JWT with scoped roles for nonpublic and mutation routes. Bounded queries, stable cursor pagination, ProblemDetails on errors. For the current offline fixture, `atSeconds` is bounded by the returned `durationSeconds` (currently 0..5400); the fixture response also carries `halfTimeSeconds`, `pitchLengthMetres` and `pitchWidthMetres` for replay and pitch rendering. Revisions with `ETag` / `If-None-Match` proposed.

These canonical routes read through Application ports backed by PostgreSQL when a connection string is configured. They are protected by the EP06-S04 `MatchRead` role policy; replay and complete evidence require `analyst` or `admin`. Azure profiles map the same protected contracts but register unavailable read adapters until an Azure PostgreSQL adapter is configured, so authenticated requests return sanitized `503 DEPENDENCY_UNAVAILABLE` and never fall back to fixtures. Azure startup requires explicit HTTPS Entra authority and audience configuration. Tenant role assignments and Azure connectivity remain unverified. `canonicalRevision` (64-bit admission revision) and `projectionRevision` (projection revision) are separate contract fields; the `revision` query parameter caps `projectionRevision`. Event/frame evidence payloads additionally return `sourceCanonicalRevision` for each referenced source record. Evidence source revision may precede the insight revision but cannot exceed the insight or selected revision, and each reference must resolve within selected time and sequence. OpenAPI source: [`openapi-canonical-bff-v1.yaml`](openapi-canonical-bff-v1.yaml).

EP08-S01 adds an **internal Application contract, not an HTTP endpoint**: `MatchIntelligenceContextBuilder` takes `(matchId, insightId, selectedTime, canonicalRevision?, projectionRevision?)`, requires a host-provided `IMatchIntelligenceScopeAuthorizer`, and reads one exact selected projection/insight plus their evidence. Its immutable packet carries both revision axes, score, selected/as-of time and sequence, algorithm/source provenance, source/state hashes, truth category, bounded evidence and explicit unknowns. It preserves the stored `observed`, `derived`, `evidence-supported-pattern`, `supported-interpretation`, `hypothesis`, and `simulated` classes as separate categories; unknown classes are refused. The packet is capped at 12 evidence items, 6 KiB UTF-8 per payload and 32 KiB serialized; persisted insight summaries are capped at 6 KiB UTF-8 in the PostgreSQL read query before materialization. The PostgreSQL reader also caps evidence item count and payload size. Source metadata, claim text and evidence payloads are labeled untrusted. Missing lineage, revision/hash mismatch, unavailable or future evidence, malformed payloads and over-cap inputs are refused; a configured-away canonical read port maps to the matching structured refusal, while cancellation propagates. No API or AgentWorker registration, model call, or Foundry interaction is implemented by this slice; host identity binding and claim publication remain unverified.

The legacy `/api/v1/matches/*` routes remain fail-closed and require the same read/replay roles; Analyst requests require `analyst` or `admin`. No fixture-backed synthetic demo is served by this runtime. Development header identity is disabled by default and may be enabled only with `Development` plus `Runtime:Profile=local`; it is a local test adapter, not an Azure identity mechanism. Canonical reads are rate limited to 120 requests per minute per remote address and Analyst actions to 30 per minute. All responses include correlation and baseline security headers; configured CORS origins must be explicit HTTPS origins (loopback HTTP is allowed only in Development).

EP04-S04 adds an internal `GetMatchAtQueryService` backed by `PostgresMatchProjectionReader`. It returns a point-in-time state and evidence-bounded replay result from PostgreSQL, pinned by selected clock, canonical admission revision and algorithm/detector version. The query is not registered in API composition and creates no additional HTTP contract. Canonical BFF handlers are mapped and protected, but Azure reads fail closed until a cloud PostgreSQL adapter is configured. Frontend scrubbing remains unverified. See the EP04-S04 work packet and PostgreSQL replay evidence for the internal contract and its test limits.

The insight DTO includes sourceVersion, sourceSha256, provenance, nullable 64-bit canonicalRevision, selectedTimeSeconds, throughSequence, policyStatus, publishable, and detector conditions when persisted insight data is available. The offline `sourceSha256` describes the synthetic fixture used by internal demo/test paths; it is not exposed by the current API. No fixture-backed demo is served. Persisted PostgreSQL reads use the validated canonical projection source hash; the route returns unavailable when its adapter is absent. The offline candidate classification (`simulated`, `unapproved-demo`, `publishable=false`, `provenance=synthetic`, `canonicalRevision=null`) is not a canonical football fact, football approval, or an implementation of the candidate Manu–Liverpool feed. Do not relabel it as evidence-supported, approved, or production-ready.

The current candidate insight also includes nullable `context` with `schemaVersion: "tactical-context-v1"`: selected-time scoreline, pressing team's `home`/`away` role, signed active-player difference for that team, reducer match phase, and the observed opponent transition from in-possession at the trigger to defending after the regain. Both offline and internal PostgreSQL replay paths derive it from the same selected-time event prefix used for the score projection. It does not infer a low block, a decision to concede possession, intent, control, or comparative tactical quality. Context is null if a selected-time state is unavailable; consumers must not substitute inferred values. This versioned field is not evidence of Product Owner or football approval.

Current insights also carry a typed `evidenceGraph` with claim, event, frame, and metric nodes; truth classes include `fact`, `derivation`, `pattern`, `interpretation`, and `hypothesis`; edges use `precedes` and `derived_from`. The graph and every node carry the same SHA-256 fingerprint of the exact serialized synthetic fixture. Each condition has an ID, observed evidence, source-node IDs, optional threshold, and an exclusion reason when it fails; the graph also carries explicit uncertainty. The offline graph marks source event/frame nodes as facts only within the synthetic fixture; graph provenance remains `synthetic`, canonical revision is null, and the pattern claim is not publishable. A metric derivation node records selected-time context and links to selected-prefix score, phase, detector-sequence events, and a source-hash-pinned active-roster node derived from `MatchState.Players[Active=true]`. A selected-context condition lists the same source nodes, so the score, phase, pressing-team role, possession transition and active-player difference have explicit graph lineage. Its `numericValue` is the signed active-player difference for the pressing team and its `unit` is `active-players`; it is reducer-derived context, not a provider performance metric. No player-performance metric nodes are emitted because none are validated. The builder rejects unresolved IDs and evidence outside the selected-time prefix. The validator refuses publishable status unless policy is approved and evidence is from a revisioned canonical source, all conditions pass, and source references resolve.

## Envelope and DTO contracts — proposed additions
`MatchTimeContext`: `{matchId,mode:'liveHead'|'selectedTime',selectedElapsedMs,period,contextRevision,canonicalRevision}`.
`Snapshot`: `{matchId,asOfElapsedMs,period,score:{home,away},status,activePlayers,frameRef?,canonicalRevision,provenance,sourceHash,coverage}`.
`InsightSummary`: `{insightId,matchId,asOfElapsedMs,truthClass,algorithmVersion,summary,conditionResults,evidenceRefs,limitations,revision}`.
`EvidenceRef`: `{kind:'event'|'frame'|'metric'|'condition',id,matchId,elapsedMs,sourceVersion,algorithmVersion,canonicalRevision}`.
`ValidatedExplanation`: `{answerId,selectedTime,audience,source:'foundry-validated'|'deterministic-fallback',text,claims:[{text,evidenceIds}],limitations,revision,modelVersion?,traceId}`.

**EP08-S02 / EP08-S04 current implementation boundary:** `PitchMind.AgentWorker.Foundry.FoundryExplanationAdapter` is a server-side internal candidate generator for Azure's OpenAI-compatible `/openai/v1/chat/completions` endpoint. It requires Azure profile endpoint/deployment configuration and managed identity, emits a strict structured candidate schema, and returns only citations whose IDs occur in the supplied selected-time packet. Its internal candidate result retains the packet SHA-256, `projectionRevision`, `ThroughSequence`, source version/provenance, source/state hashes and context-policy version so checks can bind to the exact serialized packet. `CandidateExplanationLineageChecker` recalculates packet byte size and verifies packet fingerprint/lineage, bounded candidate structure, known citations and selected-time/revision/sequence bounds, but does not establish semantic entailment; its result is never publishable. The candidate remains untrusted and is **not** the public `ValidatedExplanation`. No public explanation route, live Foundry call, Azure endpoint, or model deployment is wired or verified by this implementation. Semantic claim support and false-claim red-team proof remain open. See [ADR-011](../adr/ADR-011-foundry-candidate-adapter.md) and the [EP08-S04 work packet](../engineering/stories/EP08/EP08-S04.md).
`RealtimeCursor`: `{kind:'matchUpdated',matchId,canonicalRevision,lastSequence,serverUtc,schemaVersion}`; **payload does not carry canonical truth**.
`RealtimeNegotiateRequestV1`: `{matchId:uuid,clientRevision?:positive 64-bit canonical revision}`. `RealtimeNegotiateResponseV1`: `{transport:'aspnetcore-signalr',url:'/hubs/matches',accessToken:null,cursor,revisionChanged}` for the local adapter. `RealtimeCursorV1`: `{kind:'matchUpdated',matchId,canonicalRevision:int64,lastSequence:int64,serverUtc,schemaVersion:1}`; **payload does not carry canonical truth**. The cursor is derived only from a committed `ProjectionPublishedV1` outbox message, using its `canonicalRevision` (not `projectionRevision`) and `sequence`. Clients compare `(canonicalRevision,lastSequence)` and use canonical snapshot/backfill reads when a gap or revision change is detected; a notification is never a source of match facts. Negotiation requires an authenticated `fan`, `analyst`, or `admin` role and an existing canonical match, and is subject to the API rate limit. Group membership is match-scoped and checked on subscribe; unsubscribe removes only that connection from the group. A connection may hold at most 10 active match groups and make at most 20 unique match-subscription attempts over its lifetime; repeated active subscriptions are idempotent, and duplicate in-flight requests do not repeat the canonical lookup. Reconnect re-negotiates the current cursor and never changes canonical state. The local hub is enabled only for Development plus `Runtime:Profile=local` and `Realtime:Provider=local`; other profiles fail closed until an Azure SignalR provider is implemented.

With PostgreSQL configured to a single approved loopback host in that explicit local profile, `OutboxDispatchWorker` polls the existing leased PostgreSQL dispatcher and sends committed cursor messages through the local SignalR publisher. It is not registered for non-local profiles, missing provider configuration, or remote/multi-host PostgreSQL endpoints. This does not establish PostgreSQL-to-connected-client delivery or sequence-gap recovery.
`EventEnvelopeV1` and `TrackingFrameV1` are post-admission canonical transport contracts in [telemetry contracts v1](../data/TELEMETRY-CONTRACTS-V1.md); each requires a positive store-assigned `canonicalRevision`, distinct from `schemaVersion`. Non-negative values serialized into .NET `long` fields are bounded by `Int64.MaxValue` in the schemas. Decimal schema rules constrain supported scale and coefficient; each decimal DTO member uses `ExactDecimalJsonConverter` so default `System.Text.Json` deserialization rejects values that would overflow or lose precision. Coordinate schemas also require non-negative values while runtime validation enforces unit-specific pitch bounds. Identity strings are bounded to 128 characters, source labels/outcomes/status fields to 256, source hashes to exactly 64 lowercase hexadecimal characters, and source timestamps to 64 characters. Source hash, provenance, explicit coordinate semantics and period are mandatory where applicable. Substitutions require two distinct participant IDs, enforced by the runtime validator. Pre-admission source candidates have no canonical revision and cannot validate or publish as these DTOs. Optional event locations require their declared pitch coordinate system and the direction for the event's team. Candidate-feed mapping remains separately governed by the [simulation feed contract](../data/SIMULATION-FEED-CONTRACT.md).

## Synchronization and pagination example
1. UI chooses selected 55:08; all page queries add `atSeconds=3308` and match/contract revision. A 55:09 goal, its tactical insight, evidence and AI explanation cannot appear in this view.
2. Live cursor `lastSequence=N+1` arrives while user scrubs; show "New match update — return to live" but keep `SelectedTime`; fetch on explicit click only.
3. Historical snapshot `revision=R` and evidence `revision=R` must match. On 409 revision conflict, refetch atomic snapshot, invalidate stale queries by clientContextRevision and rerender after new evidence resolves.
4. Pagination: stable `(matchId,revision,sequence)` cursor; max proposed 100 events per page; endpoint rejects excessive unbounded requests with 400 or 413; complete data not duplicated/omitted across pages.

## Errors, security and evolution
`application/problem+json` with `type,title,status,detail,instance,correlationId` and typed `code`: `INVALID_TIME`, `SCHEMA_UNSUPPORTED`, `EVIDENCE_MISSING`, `REVISION_CONFLICT`, `INSUFFICIENT_TRACKING`, `UNAUTHORIZED`, `FORBIDDEN`, `RATE_LIMITED`, `REQUEST_TOO_LARGE`, `UNSUPPORTED_MEDIA_TYPE`, `DEPENDENCY_UNAVAILABLE`. Current verified validation, evidence, size and rate-limit failures use `INVALID_REQUEST`, `EVIDENCE_MISSING`, `REQUEST_TOO_LARGE`, `UNSUPPORTED_MEDIA_TYPE` and `RATE_LIMITED`. Use 400 for validation, 401 unauthenticated, 403 denied, 404 inaccessible/unknown, 409 revision/conflict, 413 oversized, 415 unsupported media type, 422 semantically invalid envelope, 429 exhausted rate, 503 unavailable. No sensitive provider payload in error detail.
Authentication target: Entra/OIDC auth code+PKCE; strong JWT issuer/audience/expiration signing key validation; scoped roles fan/analyst/admin; anonymous access only an owner-approved synthetic demo profile. Mutations require appropriate role, anti-CSRF where using cookies, replay/export quotas, strict CORS/CSP, no client-side Foundry credentials.
API version `v1` is additive compatible. Breaking schema/meaning change = `v2` and migration plan. Generated OpenAPI document and typed React/.NET contract tests should be published in CI. Every newly implemented endpoint must update this file and receive positive, negative, historical, authorization, rate-limit, failure and cursor tests **in the same PR**.
