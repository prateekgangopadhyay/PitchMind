# PitchMind — Consolidated API Contract and Implementation Registry
**Current baseline:** EP01-S04 contract work in progress on 2026-10-08. **Design target:** proposed `v1` extension, **NOT implemented** unless explicitly marked `CURRENT`. Source files: `src/PitchMind.Api/Program.cs`, `src/PitchMind.Contracts/V1/MatchContracts.cs`, `frontend/src/api.ts`. No missing API is assumed working because it appears here.

## Principles
Public route prefix `/api/v1`; JSON camelCase; timestamps match selected-time contract, period/added-time explicit when supported; football data exclusively from versioned synthetic JSON/authoritative projections; `X-Correlation-ID` returned in every response. All read responses include `provenance`, `sourceVersion/hash`, `canonicalRevision`, `schemaVersion` and `asOf` **once implemented**. Never leak events later than `atSeconds`. JWT with scoped roles for nonpublic and mutation routes. The fixture-backed `/api/v1/matches/*` demo routes are local-only: they are mapped only for `Development` with `Runtime:Profile=local` and return 404 in Azure profiles. They do not use Entra role authorization because they are absent in Azure. Canonical `/api/v1/canonical/*` routes are a separate family; they are not authenticated yet and cloud exposure remains blocked by EP06-S04. Bounded queries, stable cursor pagination, ProblemDetails on errors. For the current offline fixture, `atSeconds` is bounded by the returned `durationSeconds` (currently 0..5400); the fixture response also carries `halfTimeSeconds`, `pitchLengthMetres` and `pitchWidthMetres` for replay and pitch rendering. Revisions with `ETag` / `If-None-Match` proposed.

These local-only routes read the offline fixture, **not** PostgreSQL, Azure Event Hubs, Microsoft Foundry or authenticated SignalR. They are mapped only for `Development` with `Runtime:Profile=local`; Azure profiles do not map them and return 404. Successful `/api/v1` responses include `X-Contract-Version: 1` and all responses include `X-Correlation-ID`. Error bodies use `application/problem+json` with `type,title,status,code,correlationId` (plus optional `detail,instance`); the analyst limiter/framework body-size rejection retain framework-generated failure bodies until their dedicated API stories. The current fixture duration is 5400 seconds, with halftime at 2700; the service enforces the loaded fixture's own duration and halftime metadata. C# DTOs are in `PitchMind.Contracts.V1`; React consumer interfaces are in `frontend/src/api.ts`. Insight, evidence, and KeyMoment DTOs include a nullable `canonicalRevision` that is null for this demo; fixture, state, and event DTOs do not carry that property. Durable PostgreSQL revisions and correction history are not implemented.

The local key-moments endpoint scores source events with configurable, versioned demo weights and time decay. The default policy clusters same-team shots when consecutive shots are within 45 seconds; goals and cards remain individual moments. A tactical item retains event/frame evidence references and its evidence-graph claim node. The source does not define an approved “major chance” signal, so a recorded shot is not upgraded to one. This deterministic prototype policy is not Product Owner approved, and no result is publishable.

The local `evidence/{insightId}/replay` response returns `eventIds` for all graph-linked source events and `frameIds` for all graph-linked source frames; `mechanismEventIds` separately identifies the detector's mechanism events. Those references resolve exactly to evidence-graph event/frame nodes. The response includes the fixture's coordinate convention and applies it to each returned frame. Replay preserves source event IDs, sequence, clock and period without synthesizing frames or interpolating player movement. A replay is unavailable when the insight is not present at selected time or its graph references do not resolve.

EP04-S04 adds an internal PostgreSQL projection reader for selected-time and revision-bounded snapshots and event windows. It is not mapped to these local-only fixture HTTP routes; canonical HTTP access uses the separate `/api/v1/canonical/*` route family, which remains unauthenticated until EP06-S04 and must not be exposed at cloud ingress.

### Canonical BFF routes (EP06-S01; implementation evidence is in the story packet)

These routes are separately namespaced under `/api/v1/canonical/*` and read PostgreSQL projections, ledger events, and persisted insight/evidence records only. They do not fall back to the offline synthetic fixture. Without a configured PostgreSQL adapter, they return sanitized `503 DEPENDENCY_UNAVAILABLE`. Cloud exposure remains blocked on EP06-S04 or an explicitly approved synthetic public-read boundary. Malformed query parameter binding returns sanitized RFC 7807 `400 INVALID_REQUEST`; requests exceeding the server body-size limit return `413 REQUEST_TOO_LARGE`. Neither response includes framework exception details.

The `/frames` route reads only already-admitted rows from `pitchmind.tracking_frames`; it does not import the candidate JSON. Owner-declared synthetic provenance and redistribution permission are confirmed, while coordinate semantics, player metrics, canonical mappings, football realism and source admission remain under review. No candidate positions are shown until validated `TrackingFrameV1` records are admitted.

The machine-readable contract is [openapi-canonical-bff-v1.yaml](openapi-canonical-bff-v1.yaml). PostgreSQL integration tests require the isolated local database prerequisite; implementation and contract tests alone do not constitute Product Owner or football acceptance.

The current v1 DTO property names and representative JSON types are pinned by `PitchMind.Contracts.Tests`. `MatchContractMappings` is the only API mapping from the current application read models to public football response DTOs. `FixtureResponse.version` retains the source fixture version; API contract version is `X-Contract-Version`. `FixtureResponse` carries the fixture-defined duration, halftime, and pitch dimensions; frame and state DTOs describe the resulting coordinate convention. This metadata describes only the loaded fictional fixture and does not certify the supplied candidate feed's units or mappings. `MatchStateResponse` adds phase, possession, active-player counts, and player active/dismissed/yellow-card state. It preserves the existing `status` values (`replay` and `full-time`) and adds `phase` values `notstarted`, `firsthalf`, `halftime`, `secondhalf`, and `fulltime`; same-clock events are applied in source sequence order and later events are excluded. The React test fetch stubs are test-only fixtures; production UI data is loaded through `request()` and never falls back to those examples.

Current insight DTOs include `sourceVersion`, nullable `canonicalRevision`, `selectedTimeSeconds`, `throughSequence`, `policyStatus`, `publishable`, and the detector's `conditions`. The offline demo returns `classification: "simulated"`, `policyStatus: "unapproved-demo"`, `publishable: false`, and `canonicalRevision: null`; this is not a canonical football fact, football approval, or an implementation of the candidate Manu–Liverpool feed. The detector only evaluates the selected-time prefix and reports the highest included event sequence. Do not relabel this response as evidence-supported, approved, or production-ready.

The current candidate insight also includes `context`: selected-time scoreline, pressing team's `home`/`away` role, signed active-player difference for that team, reducer match phase, and the observed opponent transition from in-possession at the trigger to defending after the regain. This uses the same selected-time event prefix as the score projection. It does not infer a low block, a decision to concede possession, intent, control, or comparative tactical quality. Context is null if absent; consumers must not substitute inferred values.

Current insights also carry a typed `evidenceGraph` with claim, event, frame, and metric nodes; truth classes include `fact`, `derivation`, `pattern`, `interpretation`, and `hypothesis`; edges use `precedes` and `derived_from`. `sourceSha256` is the lowercase SHA-256 digest of the exact source bytes and appears on the graph and every node; each node must match its graph hash. `sourceVersion` remains the source schema/fixture version and `provenance` remains the source class. The graph includes typed condition evaluations (`id`, `passed`, `observed`, optional `threshold`, `sourceNodeIds`, and optional `exclusionReason`) plus an `uncertainty` statement. Failed evaluations require an exclusion reason; all referenced node IDs must resolve. The offline graph marks source event/frame nodes as facts only within the synthetic fixture; graph provenance remains `synthetic`, canonical revision is null, and the pattern claim is not publishable. A metric derivation node records selected-time context and links to the selected-prefix score, lineup, phase and detector events. Its `numericValue` is the signed active-player difference for the pressing team and its `unit` is `active-players`; it is reducer-derived context, not a provider performance metric. No player-performance metric nodes are emitted because none are validated. The builder rejects unresolved IDs and evidence outside the selected-time prefix. The validator rejects unsupported truth labels and hash mismatches, blocks publication of hypotheses or claims with failed/missing conditions, and refuses any other publishable status unless policy is approved and evidence is from a revisioned canonical source. Confidence is not calculated because this demonstration detector has no calibrated confidence model.

**EP06-S04 route boundary (cross-story contract alignment):** fixture-backed `/api/v1/matches/*` demo routes are mapped only for `Development` with `Runtime:Profile=local`; they are absent (404) in Azure profiles. Canonical `/api/v1/canonical/*` routes remain separately authenticated and protected. The synthetic graph contract above does not authorize fixture data in Azure.

## Envelope and DTO contracts — proposed additions
`MatchTimeContext`: `{matchId,mode:'liveHead'|'selectedTime',selectedElapsedMs,period,contextRevision,canonicalRevision}`.
`Snapshot`: `{matchId,asOfElapsedMs,period,score:{home,away},status,activePlayers,frameRef?,canonicalRevision,provenance,sourceHash,coverage}`.
`InsightSummary`: `{insightId,matchId,asOfElapsedMs,truthClass,algorithmVersion,summary,conditionResults,evidenceRefs,limitations,revision}`.
`EvidenceRef`: `{kind:'event'|'frame'|'metric'|'condition',id,matchId,elapsedMs,sourceVersion,algorithmVersion,canonicalRevision}`.
`ValidatedExplanation`: `{answerId,selectedTime,audience,source:'foundry-validated'|'deterministic-fallback',text,claims:[{text,evidenceIds}],limitations,revision,modelVersion?,traceId}`.
`RealtimeCursor`: `{kind:'matchUpdated',matchId,canonicalRevision,lastSequence,serverUtc,schemaVersion}`; **payload does not carry canonical truth**.
`EventEnvelopeV1` and `TrackingFrameV1` are versioned transport contracts in [telemetry contracts v1](../data/TELEMETRY-CONTRACTS-V1.md); source hash, provenance, explicit coordinate semantics and period are mandatory where applicable. Optional event locations require their declared pitch coordinate system. Candidate-feed mapping remains separately governed by the [simulation feed contract](../data/SIMULATION-FEED-CONTRACT.md).

## Synchronization and pagination example
1. UI chooses selected 55:08; all page queries add `atSeconds=3308` and match/contract revision. A 55:09 goal, its tactical insight, evidence and AI explanation cannot appear in this view.
2. Live cursor `lastSequence=N+1` arrives while user scrubs; show "New match update — return to live" but keep `SelectedTime`; fetch on explicit click only.
3. Historical snapshot `revision=R` and evidence `revision=R` must match. On 409 revision conflict, refetch atomic snapshot, invalidate stale queries by clientContextRevision and rerender after new evidence resolves.
4. Pagination: stable `(matchId,revision,sequence)` cursor; max proposed 100 events per page; endpoint rejects excessive unbounded requests with 400 or 413; complete data not duplicated/omitted across pages.

## Errors, security and evolution
`application/problem+json` with `type,title,status,detail,instance,correlationId` and typed `code`: `INVALID_TIME`, `SCHEMA_UNSUPPORTED`, `EVIDENCE_MISSING`, `REVISION_CONFLICT`, `INSUFFICIENT_TRACKING`, `UNAUTHORIZED`, `FORBIDDEN`, `RATE_LIMITED`, `DEPENDENCY_UNAVAILABLE`. The currently mapped validation and evidence failures use `INVALID_REQUEST` and `EVIDENCE_MISSING`; middleware/framework-generated 413 and 429 responses are not yet normalized. Use 400 for validation, 401 unauthenticated, 403 denied, 404 inaccessible/unknown, 409 revision/conflict, 413 oversized, 422 semantically invalid envelope, 429 exhausted rate, 503 unavailable. No sensitive provider payload in error detail.
Authentication target: Entra/OIDC auth code+PKCE; strong JWT issuer/audience/expiration signing key validation; scoped roles fan/analyst/admin; anonymous access only an owner-approved synthetic demo profile. Mutations require appropriate role, anti-CSRF where using cookies, replay/export quotas, strict CORS/CSP, no client-side Foundry credentials.
API version `v1` is additive compatible. Breaking schema/meaning change = `v2` and migration plan. Generated OpenAPI document and typed React/.NET contract tests should be published in CI. Every newly implemented endpoint must update this file and receive positive, negative, historical, authorization, rate-limit, failure and cursor tests **in the same PR**.

## Supplied source feed compatibility gap (2026-10-08)
The user-supplied [Manchester United–Liverpool source profile](../data/MANU-LIV-SOURCE-PROFILE.md) shows source `sequence` **1..2199** (synthetic-v2 test fixture starts 0), `clockSeconds` **0..5761** with added time (current offline API clamps at 5400), **19 source event types** versus the current **11-value synthetic `MatchEventType` enum**, and **0–100-looking coordinates** rather than metres. The existing `SyntheticFixtureGenerator` and `SyntheticMatchService` MUST NOT be advertised as serving this feed. Adapter and API changes need versioned clock/coordinate/event type contracts and regression tests; missing coverage is expressed as unavailable.
