# PitchMind — Consolidated API Contract and Implementation Registry
**Current baseline:** the candidate-feed API and PostgreSQL-backed canonical BFF are separate route families. DEV uses the Azure profile; LOCAL's Docker adapters are not part of DEV. Azure adapters and Bicep declarations show intended composition, not live-connectivity evidence. The current DEV resource inventory is summarized in the [DEV integration status](../engineering/AZURE-DEV-LIVE-INTEGRATION-STATUS.md). Recent owner-supplied candidate analyst calls returned `503 ANALYST_UNAVAILABLE`; do not infer successful Foundry responses from source composition. The latest browser token error is historical and should not be treated as proof of the current identity setup. Source files: `src/PitchMind.Api/Program.cs`, `src/PitchMind.Api/CanonicalMatchEndpoints.cs`, `src/PitchMind.Api/ApiSecurity.cs`, `src/PitchMind.Contracts/V1/MatchContracts.cs`, `frontend/src/api.ts`.

## Principles
Public route prefix `/api/v1`; JSON camelCase; timestamps match selected-time contract, period/added-time explicit when supported; canonical football data comes only from admitted versioned sources or authoritative projections; `X-Correlation-ID` returned in every response. All read responses include `provenance`, `sourceVersion/hash`, `canonicalRevision`, `schemaVersion` and `asOf` **once implemented**. Never leak events later than `atSeconds`. JWT with scoped roles for nonpublic and mutation routes. Bounded queries, stable cursor pagination, ProblemDetails on errors. The legacy offline fixture response is not served by production API routes; its DTO/UI scaffolding remains for the legacy demo path, while fixture data and generation are test-only. The response contract bounds `atSeconds` by `durationSeconds` (currently 0..5400) and also carries `halfTimeSeconds`, `pitchLengthMetres` and `pitchWidthMetres` for replay and pitch rendering. Revisions with `ETag` / `If-None-Match` proposed.

## Operational metrics export (EP06-S05)

The API has no public metrics route. OTLP export is disabled unless `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT` or `OTEL_EXPORTER_OTLP_ENDPOINT` is explicitly configured. The exporter includes only `PitchMind.Api` and `PitchMind.Infrastructure.Outbox` meters. Remote/non-local profiles require an HTTPS endpoint; HTTP is permitted only in the explicit Development/local profile. No collector or cloud destination is configured or provisioned by this repository change. For Azure environments, the deployment configuration must point this endpoint to an approved Azure Monitor or Azure-hosted OpenTelemetry collector.

The exported API instruments use route templates, bounded HTTP method names and response status classes; match, event, insight, user, query and correlation identifiers are excluded from metric dimensions. The outbox meter reports publication/retry/dead-letter counts and age when a durable message is dispatched. These metrics do not measure browser receipt lag or client reconnect state, and no latency or availability target is claimed until an SRE records measured values.

These canonical routes read through Application ports backed by PostgreSQL when a connection string is configured. They are protected by the EP06-S04 `MatchRead` role policy; replay and complete evidence require `analyst` or `admin`. The frame endpoint requires `MatchReplay` (`analyst` or `admin`). Azure profiles use the Entra-authenticated PostgreSQL data source when configured, otherwise register unavailable read adapters; requests fail with sanitized `503 DEPENDENCY_UNAVAILABLE` and never fall back to fixtures. Azure startup requires explicit HTTPS Entra authority and audience configuration. Tenant role assignments and Azure connectivity remain unverified. `canonicalRevision` (64-bit admission revision) and `projectionRevision` (projection revision) are separate contract fields; the `revision` query parameter caps `projectionRevision`. Frame reads match exact selected elapsed time, source hash and canonical revision, validate the versioned telemetry schema and do not interpolate positions. A `frameId` lookup may include `sourceRevision` to request that exact source row when multiple canonical revisions share an ID; the source revision must be positive and no greater than the selected canonical revision. Malformed or semantically invalid persisted frames return sanitized `503 CANONICAL_DATA_INVALID`. Their opaque cursor binds match, selected time, both revisions, source hash and the stable `(sequence,frameId)` key. Event/frame evidence payloads additionally return `sourceCanonicalRevision` for each referenced source record. Evidence source revision may precede the insight revision but cannot exceed the insight or selected revision, and each reference must resolve within selected time and sequence. OpenAPI source: [`openapi-canonical-bff-v1.yaml`](openapi-canonical-bff-v1.yaml).

Canonical insight and evidence responses include the stored `conditions` JSON object. `limitations` is returned as `null` when no limitation records are persisted; consumers must present that state as unrecorded rather than inventing limitations. Insight conditions are validated as JSON objects before response materialization.

EP08-S01 adds an **internal Application contract, not an HTTP endpoint**: `MatchIntelligenceContextBuilder` takes `(matchId, insightId, selectedTime, canonicalRevision?, projectionRevision?)`, requires a host-provided `IMatchIntelligenceScopeAuthorizer`, and reads one exact selected projection/insight plus their evidence. Its immutable packet carries both revision axes, score, selected/as-of time and sequence, algorithm/source provenance, source/state hashes, truth category, bounded evidence and explicit unknowns. It preserves the stored `observed`, `derived`, `evidence-supported-pattern`, `supported-interpretation`, `hypothesis`, and `simulated` classes as separate categories; unknown classes are refused. The packet is capped at 12 evidence items, 6 KiB UTF-8 per payload and 32 KiB serialized; persisted insight summaries are capped at 6 KiB UTF-8 in the PostgreSQL read query before materialization. The PostgreSQL reader also caps evidence item count and payload size. Source metadata, claim text and evidence payloads are labeled untrusted. Missing lineage, revision/hash mismatch, unavailable or future evidence, malformed payloads and over-cap inputs are refused; a configured-away canonical read port maps to the matching structured refusal, while cancellation propagates. No API or AgentWorker registration, model call, or Foundry interaction is implemented by this slice; host identity binding and claim publication remain unverified.

The legacy `/api/v1/matches/*` routes remain fail-closed and require the same read/replay roles; Analyst requests require `analyst` or `admin`. No fixture-backed synthetic demo is served by this runtime. Development header identity is disabled by default and may be enabled only with `Development` plus `Runtime:Profile=local`; it is a local test adapter, not an Azure identity mechanism. Canonical reads are rate limited to 120 requests per minute per remote address and Analyst actions to 30 per minute. All responses include correlation and baseline security headers; configured CORS origins must be explicit HTTPS origins (loopback HTTP is allowed only in Development).

EP04-S04 includes an internal `GetMatchAtQueryService` backed by `PostgresMatchProjectionReader`, which may produce evidence-bounded detector output for internal use. A separate `ReplayCanonicalMatchStateService` is exposed through `GET /api/v1/canonical/matches/{matchId}/replay/deterministic`; it replays the immutable event prefix, checks the selected persisted state digest, and returns only canonical state, a bounded event page, and input/state digests. It never runs or returns detector output. The API is analyst/admin-only and fails closed for malformed or mismatching stored inputs. Azure reads fail closed until a cloud PostgreSQL adapter is configured. Frontend scrubbing remains unverified. See the EP04-S04 work packet and evidence for verified scope and limits.

The insight DTO includes sourceVersion, sourceSha256, provenance, nullable 64-bit canonicalRevision, selectedTimeSeconds, throughSequence, policyStatus, publishable, and detector conditions when persisted insight data is available. The offline `sourceSha256` describes the synthetic fixture used by internal demo/test paths; it is not exposed by the current API. No fixture-backed demo is served. Persisted PostgreSQL reads use the validated canonical projection source hash; the route returns unavailable when its adapter is absent. The offline candidate classification (`simulated`, `unapproved-demo`, `publishable=false`, `provenance=synthetic`, `canonicalRevision=null`) is not a canonical football fact, football approval, or an implementation of the candidate Manu–Liverpool feed. Do not relabel it as evidence-supported, approved, or production-ready.

The current candidate insight also includes nullable `context` with `schemaVersion: "tactical-context-v1"`: selected-time scoreline, pressing team's `home`/`away` role, signed active-player difference for that team, reducer match phase, and the observed opponent transition from in-possession at the trigger to defending after the regain. Both offline and internal PostgreSQL replay paths derive it from the same selected-time event prefix used for the score projection. It does not infer a low block, a decision to concede possession, intent, control, or comparative tactical quality. Context is null if a selected-time state is unavailable; consumers must not substitute inferred values. This versioned field is not evidence of Product Owner or football approval.

Current insights also carry a typed `evidenceGraph` with claim, event, frame, and metric nodes; truth classes include `fact`, `derivation`, `pattern`, `interpretation`, and `hypothesis`; edges use `precedes` and `derived_from`. The graph and every node carry the same SHA-256 fingerprint of the exact serialized synthetic fixture. Each condition has an ID, observed evidence, source-node IDs, optional threshold, and an exclusion reason when it fails; the graph also carries explicit uncertainty. The offline graph marks source event/frame nodes as facts only within the synthetic fixture; graph provenance remains `synthetic`, canonical revision is null, and the pattern claim is not publishable. A metric derivation node records selected-time context and links to selected-prefix score, phase, detector-sequence events, and a source-hash-pinned active-roster node derived from `MatchState.Players[Active=true]`. A selected-context condition lists the same source nodes, so the score, phase, pressing-team role, possession transition and active-player difference have explicit graph lineage. Its `numericValue` is the signed active-player difference for the pressing team and its `unit` is `active-players`; it is reducer-derived context, not a provider performance metric. No player-performance metric nodes are emitted because none are validated. The builder rejects unresolved IDs and evidence outside the selected-time prefix. The validator refuses publishable status unless policy is approved and evidence is from a revisioned canonical source, all conditions pass, and source references resolve.

**EP08-S02 / EP08-S04 current implementation boundary:** `PitchMind.AgentWorker.Foundry.FoundryExplanationAdapter` is a server-side internal candidate generator with two configured transports: Azure OpenAI-compatible `/openai/v1/chat/completions` using `Foundry:Endpoint` + `Foundry:Deployment`, or a Foundry project agent Responses endpoint using `Foundry:Mode=ProjectAgent`, `Foundry:Endpoint=https://<resource>.services.ai.azure.com/api/projects/<project>`, and `Foundry:AgentName` (default `TacticalAnalyst`). Project-agent mode uses managed identity for `https://ai.azure.com/.default`; model-deployment mode uses the Cognitive Services scope. Both emit a strict structured candidate and reject citations not in the supplied selected-time packet. `tactical-agents.v1.json` contains nine specialist strategy profiles plus an evidence-first default; these are local prompt profiles and do not imply nine remote Foundry agents exist. The selected profile's bounded strategy context and up to three profile-filtered knowledge cards are passed with the evidence packet. The internal candidate retains packet SHA-256, `projectionRevision`, `ThroughSequence`, source version/provenance, source/state hashes and context-policy version. The lineage checker verifies packet fingerprint/lineage, bounded structure, citations and selected-time/revision/sequence bounds, but not semantic entailment. The source-text guard is narrow: one claim must restate the selected insight and cite its full evidence set; it does not prove that insight or arbitrary language semantically correct. The candidate is untrusted and is **not** the public `ValidatedExplanation`. No public explanation route, live Foundry call, remote agent update, or production model deployment has been verified. Semantic claim support and false-claim red-team proof remain open. See [ADR-011](../adr/ADR-011-foundry-candidate-adapter.md) and the [EP08-S04 work packet](../engineering/stories/EP08/EP08-S04.md).

**EP08-S03 internal orchestration boundary:** `ExplanationAgentOrchestrator` is a bounded library component, not an HTTP contract or active AgentWorker consumer. It calls a pre-authorized read-only context tool, one candidate generator and the deterministic verifier; only verifier output is returned. The host must bind authorization to its authenticated caller before supplying the context tool. Rejected candidate text/citations are not exposed in results or traces. No public route, live Foundry request, or authenticated host composition is implemented by this slice; selected time currently follows the 0..5400 request contract. See [ADR-012](../adr/ADR-012-bounded-agent-handoffs.md) and the [EP08-S03 work packet](../engineering/stories/EP08/EP08-S03.md).
`RealtimeCursor`: `{kind:'matchUpdated',matchId,canonicalRevision,lastSequence,serverUtc,schemaVersion}`; **payload does not carry canonical truth**.
`RealtimeNegotiateRequestV1`: `{matchId:uuid,clientRevision?:positive 64-bit canonical revision}`. `RealtimeNegotiateResponseV1`: `{transport:'aspnetcore-signalr',url:'/hubs/matches',accessToken:null,cursor,revisionChanged}` for the local adapter. `RealtimeCursorV1`: `{kind:'matchUpdated',matchId,canonicalRevision:int64,lastSequence:int64,serverUtc,schemaVersion:1}`; **payload does not carry canonical truth**. The cursor is derived only from a committed `ProjectionPublishedV1` outbox message, using its `canonicalRevision` (not `projectionRevision`) and `sequence`. Clients compare `(canonicalRevision,lastSequence)` and use canonical snapshot/backfill reads when a gap or revision change is detected; a notification is never a source of match facts. Negotiation requires an authenticated `fan`, `analyst`, or `admin` role and an existing canonical match, and is subject to the API rate limit. Group membership is match-scoped and checked on subscribe; unsubscribe removes only that connection from the group. A connection may hold at most 10 active match groups and make at most 20 unique match-subscription attempts over its lifetime; repeated active subscriptions are idempotent, and duplicate in-flight requests do not repeat the canonical lookup. Reconnect re-negotiates the current cursor and never changes canonical state. The local hub is enabled only for Development plus `Runtime:Profile=local` and `Realtime:Provider=local`. Azure candidate realtime uses the same hub path with the Azure SignalR provider when `Runtime:Profile=azure` and `CandidateFeed:Enabled=true`; both require configured identity and service endpoints.

Browser SignalR `accessTokenFactory` credentials use the Authorization header for negotiate and HTTP backfill; browser WebSocket/SSE transports send their bearer as `access_token` in the hub URL. Entra JWT validation accepts that query token only on the exact `/hubs/matches` path; API routes, `/negotiate`, and other paths do not accept query credentials. The opt-in local Development header adapter accepts a bounded unsigned `pmdev.v1` bearer for browser testing, including the exact hub path; this adapter is local-only and cannot be used as Azure identity. Any future reverse-proxy request logging must redact the hub query token.

With PostgreSQL configured to a single approved loopback host in that explicit local profile, `OutboxDispatchWorker` polls the existing leased PostgreSQL dispatcher and sends committed cursor messages through the local SignalR publisher. It is not registered for non-local profiles, missing provider configuration, or remote/multi-host PostgreSQL endpoints. This does not establish PostgreSQL-to-connected-client delivery or sequence-gap recovery.

The realtime client can use an explicit authenticated HTTP refresh against canonical backfill when SignalR negotiation or startup fails. A failed refresh marks the view stale and leaves retry available; a successful refresh does not restore the realtime connection. The fixture/demo `App` does not mount this component because it has no canonical match context or identity provider, so this is a client integration boundary rather than a connected browser flow.
`EventEnvelopeV1` and `TrackingFrameV1` are post-admission canonical transport contracts in [telemetry contracts v1](../data/TELEMETRY-CONTRACTS-V1.md); each requires a positive store-assigned `canonicalRevision`, distinct from `schemaVersion`. Non-negative values serialized into .NET `long` fields are bounded by `Int64.MaxValue` in the schemas. Decimal schema rules constrain supported scale and coefficient; each decimal DTO member uses `ExactDecimalJsonConverter` so default `System.Text.Json` deserialization rejects values that would overflow or lose precision. Coordinate schemas also require non-negative values while runtime validation enforces unit-specific pitch bounds. Identity strings are bounded to 128 characters, source labels/outcomes/provenance statuses to 256, source hashes to exactly 64 lowercase hexadecimal characters, and source timestamps to 64 characters. `source.rightsReviewStatus` must be exactly `approved_for_use`, which means independent review approved that source for canonical use; owner-declared provenance or `reviewed` alone is insufficient. Source hash, provenance, explicit coordinate semantics and period are mandatory where applicable. Substitutions require two distinct participant IDs, enforced by the runtime validator. Pre-admission source candidates have no canonical revision and cannot validate or publish as these DTOs. Optional event locations require their declared pitch coordinate system and the direction for the event's team. Candidate-feed mapping remains separately governed by the [simulation feed contract](../data/SIMULATION-FEED-CONTRACT.md).

## Synchronization and pagination example
1. UI chooses selected 55:08; all page queries add `atSeconds=3308` and match/contract revision. A 55:09 goal, its tactical insight, evidence and AI explanation cannot appear in this view.
2. On initial load, request canonical backfill from `afterSequence=-1`, negotiate realtime, join the match group, then backfill again to close the race between snapshot and group subscription.
3. A newer cursor triggers canonical backfill. Revision mismatch or cursor ahead of durable head restarts from sequence -1; duplicate pages are reduced idempotently.
4. If a live cursor arrives while the viewer is in historical mode, show a nonintrusive update indicator and keep `SelectedTime`; refresh only after the user explicitly returns to LIVE. A cursor alone does not prove a new insight exists.
5. Historical snapshot revision and evidence revision must match. On 409, refetch an atomic snapshot and invalidate stale queries before rendering resolved evidence.
6. Pagination uses a stable `(matchId,revision,sequence)` cursor and at most 100 events per page; excessive or unbounded requests fail, and adjacent pages neither duplicate nor omit data.

## Errors, security and evolution
`application/problem+json` with `type,title,status,detail,instance,correlationId` and typed `code`: `INVALID_TIME`, `SCHEMA_UNSUPPORTED`, `EVIDENCE_MISSING`, `REVISION_CONFLICT`, `INSUFFICIENT_TRACKING`, `UNAUTHORIZED`, `FORBIDDEN`, `RATE_LIMITED`, `REQUEST_TOO_LARGE`, `UNSUPPORTED_MEDIA_TYPE`, `DEPENDENCY_UNAVAILABLE`. Current verified validation, evidence, size and rate-limit failures use `INVALID_REQUEST`, `EVIDENCE_MISSING`, `REQUEST_TOO_LARGE`, `UNSUPPORTED_MEDIA_TYPE` and `RATE_LIMITED`. Use 400 for validation, 401 unauthenticated, 403 denied, 404 inaccessible/unknown, 409 revision/conflict, 413 oversized, 415 unsupported media type, 422 semantically invalid envelope, 429 exhausted rate, 503 unavailable. No sensitive provider payload in error detail.
Authentication target: Entra/OIDC auth code+PKCE; strong JWT issuer/audience/expiration signing key validation; scoped roles fan/analyst/admin; anonymous access only an owner-approved synthetic demo profile. Mutations require appropriate role, anti-CSRF where using cookies, replay/export quotas, strict CORS/CSP, no client-side Foundry credentials.
API version `v1` is additive compatible. Breaking schema/meaning change = `v2` and migration plan. Generated OpenAPI document and typed React/.NET contract tests should be published in CI. Every newly implemented endpoint must update this file and receive positive, negative, historical, authorization, rate-limit, failure and cursor tests **in the same PR**.
