# PitchMind — Consolidated API Contract and Implementation Registry
**Current baseline:** EP06-S04 local auth boundary implemented on a draft stack from PR #81. **Design target:** proposed `v1` extension, **NOT implemented** unless explicitly marked `CURRENT`. Source files: `src/PitchMind.Api/Program.cs`, `src/PitchMind.Contracts/V1/MatchContracts.cs`, `frontend/src/api.ts`. No missing API is assumed working because it appears here.

## Principles
Public route prefix `/api/v1`; JSON camelCase; timestamps match selected-time contract, period/added-time explicit when supported; football data exclusively from versioned synthetic JSON/authoritative projections; `X-Correlation-ID` returned in every response. Never leak events later than `atSeconds`. Canonical BFF routes require JWT authentication, a configured read role, and a configured match-entitlement claim whose value matches the route match ID. Canonical fixture enumeration separately requires a configured catalog role. The local synthetic demo routes are anonymous only inside `Development` with `Runtime:Profile=local`, return 404 elsewhere, and mark responses `X-Data-Class: synthetic-demo`. Authority, audience, role claim type, match-entitlement claim type and read roles have no repository defaults; missing or invalid auth configuration fails closed. The deployment owner must supply the actual Entra values before canonical cloud access can work. Bounded queries, stable cursor pagination, ProblemDetails on errors. For the current offline fixture, `atSeconds` is bounded by the returned `durationSeconds` (currently 0..5400); the fixture response also carries `halfTimeSeconds`, `pitchLengthMetres` and `pitchWidthMetres` for replay and pitch rendering. Revisions with `ETag` / `If-None-Match` proposed.

### Canonical BFF routes (EP06-S01; implementation evidence is in the story packet)

These routes are separately namespaced under `/api/v1/canonical/*` and read PostgreSQL projections, ledger events, and persisted insight/evidence records only. They do not fall back to the offline synthetic fixture. Each route requires a configured read role and an entitlement claim matching that route's `matchId`; catalogue listing requires a separately configured catalog role. Without configured valid JWT settings the routes fail closed. Without a PostgreSQL adapter, an authorized request returns sanitized `503 DEPENDENCY_UNAVAILABLE`. Malformed query parameter binding returns sanitized RFC 7807 `400 INVALID_REQUEST`; requests exceeding 4 KiB return `413 REQUEST_TOO_LARGE`; exhausted rate-limit partitions return `429 RATE_LIMITED`. Authenticated requests partition by a SHA-256 digest of the validated `sub` claim; traffic without an authenticated subject falls back to the connection IP. Neither response includes framework exception details. The candidate has no production issuer, audience, claim-type, role, or CORS-origin values; operations must provide these before cloud access can work.

The machine-readable contract is [openapi-canonical-bff-v1.yaml](openapi-canonical-bff-v1.yaml). PostgreSQL integration tests require the isolated local database prerequisite; implementation and contract tests alone do not constitute Product Owner or football acceptance.

The current v1 DTO property names and representative JSON types are pinned by `PitchMind.Contracts.Tests`. `MatchContractMappings` is the only API mapping from the current application read models to public football response DTOs. `FixtureResponse.version` retains the source fixture version; API contract version is `X-Contract-Version`. `FixtureResponse` carries the fixture-defined duration, halftime, and pitch dimensions; frame and state DTOs describe the resulting coordinate convention. This metadata describes only the loaded fictional fixture and does not certify the supplied candidate feed's units or mappings. `MatchStateResponse` adds phase, possession, active-player counts, and player active/dismissed/yellow-card state. It preserves the existing `status` values (`replay` and `full-time`) and adds `phase` values `notstarted`, `firsthalf`, `halftime`, `secondhalf`, and `fulltime`; same-clock events are applied in source sequence order and later events are excluded. The React test fetch stubs are test-only fixtures; production UI data is loaded through `request()` and never falls back to those examples.

Current insight DTOs include `sourceVersion`, nullable `canonicalRevision`, `selectedTimeSeconds`, `throughSequence`, `policyStatus`, `publishable`, and the detector's `conditions`. The offline demo returns `classification: "simulated"`, `policyStatus: "unapproved-demo"`, `publishable: false`, and `canonicalRevision: null`; this is not a canonical football fact, football approval, or an implementation of the candidate Manu–Liverpool feed. The detector only evaluates the selected-time prefix and reports the highest included event sequence. Do not relabel this response as evidence-supported, approved, or production-ready.

The current candidate insight also includes `context`: selected-time scoreline, pressing team's `home`/`away` role, signed active-player difference for that team, reducer match phase, and the observed opponent transition from in-possession at the trigger to defending after the regain. This uses the same selected-time event prefix as the score projection. It does not infer a low block, a decision to concede possession, intent, control, or comparative tactical quality. Context is null if absent; consumers must not substitute inferred values.

Current insights also carry a typed `evidenceGraph` with claim, event, frame, and metric nodes; truth classes include `fact`, `derivation`, `pattern`, `interpretation`, and `hypothesis`; edges use `precedes` and `derived_from`. `sourceSha256` is the lowercase SHA-256 digest of the exact source bytes and appears on the graph and every node; each node must match its graph hash. `sourceVersion` remains the source schema/fixture version and `provenance` remains the source class. The graph includes typed condition evaluations (`id`, `passed`, `observed`, optional `threshold`, `sourceNodeIds`, and optional `exclusionReason`) plus an `uncertainty` statement. Failed evaluations require an exclusion reason; all referenced node IDs must resolve. The offline graph marks source event/frame nodes as facts only within the synthetic fixture; graph provenance remains `synthetic`, canonical revision is null, and the pattern claim is not publishable. A metric derivation node records selected-time context and links to the selected-prefix score, lineup, phase and detector events. Its `numericValue` is the signed active-player difference for the pressing team and its `unit` is `active-players`; it is reducer-derived context, not a provider performance metric. No player-performance metric nodes are emitted because none are validated. The builder rejects unresolved IDs and evidence outside the selected-time prefix. The validator rejects unsupported truth labels and hash mismatches, blocks publication of hypotheses or claims with failed/missing conditions, and refuses any other publishable status unless policy is approved and evidence is from a revisioned canonical source. Confidence is not calculated because this demonstration detector has no calibrated confidence model.

**EP06-S04 route boundary (cross-story contract alignment):** fixture-backed `/api/v1/matches/*` demo routes are anonymous only in `Development` with `Runtime:Profile=local`; they are absent (404) in other profiles and each response includes `X-Data-Class: synthetic-demo`. Canonical `/api/v1/canonical/*` routes require configured JWT bearer validation, a configured read role, and a claim containing the exact requested match GUID. Cross-match fixture enumeration requires a separate configured catalog role. This implementation does not authorize fixture data in Azure.

Per connection, subscribe and unsubscribe calls share a fixed one-minute limit configured by `Realtime:MaximumHubMethodCallsPerMinute` (default 30); invalid/non-positive explicit configuration rejects all such calls. Group membership is match-scoped and checked on subscribe; unsubscribe removes only the caller's connection from that group. Reconnect re-negotiates the current cursor and never changes canonical state. The local hub is enabled only for `Development` plus `Runtime:Profile=local` and `Realtime:Provider=local`. Missing provider configuration fails closed, and the worker is not registered in Azure profiles or when PostgreSQL points to a remote/multi-host endpoint. Tests cover those guards plus worker invocation, cancellation, and retry after an unexpected dispatcher exception; database-to-connected-client delivery and ordered reconnect/backfill remain unverified.

## Synchronization and pagination example
1. UI chooses selected 55:08; all page queries add `atSeconds=3308` and match/contract revision. A 55:09 goal, its tactical insight, evidence and AI explanation cannot appear in this view.
2. On initial load, request backfill from `afterSequence=-1`, negotiate realtime, join the match group, then request backfill again to close the race between the initial snapshot and group subscription.
3. A cursor notification with a newer `(canonicalRevision,lastSequence)` triggers canonical backfill. A revision mismatch or cursor ahead of the durable head restarts from sequence -1; duplicate pages are reduced idempotently. The browser follows each `hasMore` page only when its `nextCursor` is present and the applied revision/through-sequence advances, up to 100 pages per refresh. If a live cursor arrives during an in-flight request and its no-more response is behind the observed cursor, the client makes one fresh backfill request; if that retry is still stale or makes no progress, catch-up stops and the timeline remains marked behind/disconnected. Missing/repeated cursors, no-progress pages, sequence gaps, lifecycle aborts, or changed match/time context also stop catch-up and leave it marked behind.
4. If a live cursor arrives while the viewer is in `HISTORICAL` mode, show a nonintrusive update indicator and keep `SelectedTime`; refresh the selected view only after the user explicitly returns to LIVE. The cursor alone does not prove that a new insight exists.
5. Historical snapshot `revision=R` and evidence `revision=R` must match. On 409 revision conflict, refetch atomic snapshot, invalidate stale queries by clientContextRevision and rerender after new evidence resolves.
6. Pagination: stable `(matchId,revision,sequence)` cursor; max 100 events per page; endpoint rejects excessive unbounded requests with 400 or 413; complete data not duplicated/omitted across pages.

## Errors, security and evolution
`application/problem+json` with `type,title,status,detail,instance,correlationId` and typed `code`: `INVALID_TIME`, `SCHEMA_UNSUPPORTED`, `EVIDENCE_MISSING`, `REVISION_CONFLICT`, `INSUFFICIENT_TRACKING`, `UNAUTHORIZED`, `FORBIDDEN`, `RATE_LIMITED`, `REQUEST_TOO_LARGE`, `DEPENDENCY_UNAVAILABLE`. The current body-size and limiter responses are normalized. Use 400 for validation, 401 unauthenticated, 403 denied, 404 inaccessible/unknown, 409 revision/conflict, 413 oversized, 422 semantically invalid envelope, 429 exhausted rate, 503 unavailable. No sensitive provider payload in error detail.
Current auth implementation: ASP.NET JWT bearer validates HTTPS authority metadata, exact configured issuer and audience, signed keys and token lifetime. `Authentication:RoleClaimType` and `Authentication:MatchEntitlementClaimType` select the token claim types; `Authorization:ReadRoles` is a comma-separated operator value. For each canonical match route, the entitlement claim must contain the requested GUID. Cross-match fixture catalogue access also requires one of `Authorization:CatalogRoles`; it is denied when that setting is empty. Missing/malformed auth config, including a non-HTTPS authority, fails closed. For browser SignalR transports, JWT bearer reads `access_token` from the query string only under `/hubs/matches`; other API paths ignore query tokens. The `Microsoft.AspNetCore.Hosting` logger is filtered to `Warning` or higher because ASP.NET Core hosting request diagnostics include the full URL, including SignalR's query token ([Microsoft SignalR security guidance](https://learn.microsoft.com/en-us/aspnet/core/signalr/security?view=aspnetcore-10.0)). Deployment logging configuration must not set `Microsoft.AspNetCore.Hosting.Diagnostics` below Warning. Application audit logging records only the path; configure proxy/access logs to redact query strings as well. Local `/api/v1/matches/*` synthetic demo data is anonymous only in `Development` + `Runtime:Profile=local`; the routes are not mapped in other profiles and explicitly mark their responses synthetic. There are no production issuer, audience, role or claim-type values in source control, and no deployment configuration has been supplied. CORS origins remain operator-configured; no origin is allowed by default. Canonical read limit defaults to 60 requests per authenticated subject per minute, keyed by a SHA-256 digest of the validated `sub` claim, with connection-IP fallback when a subject is absent; realtime negotiation defaults to 20 requests per subject per minute with the same fallback. Both custom negotiation and the SignalR hub mapping (including its negotiate endpoint) carry the realtime limiter. Request bodies are limited to 4 KiB; realtime inbound messages are 4 KiB; concurrent connections are capped; subscribe/unsubscribe hub methods share a per-connection one-minute limit configurable by `Realtime:MaximumHubMethodCallsPerMinute` (default 30); and distinct active match groups per connection are capped by `Realtime:MaximumActiveMatchSubscriptionsPerConnection` (default 4), with reservations released on rejected authorization, successful unsubscribe, or disconnect. These defaults are implementation safeguards, not measured service SLOs. No client-side Foundry credentials.
API version `v1` is additive compatible. Breaking schema/meaning change = `v2` and migration plan. Generated OpenAPI document and typed React/.NET contract tests should be published in CI. Every newly implemented endpoint must update this file and receive positive, negative, historical, authorization, rate-limit, failure and cursor tests **in the same PR**.

## Supplied source feed compatibility gap (2026-10-08)
The user-supplied [Manchester United–Liverpool source profile](../data/MANU-LIV-SOURCE-PROFILE.md) shows source `sequence` **1..2199** (synthetic-v2 test fixture starts 0), `clockSeconds` **0..5761** with added time (current offline API clamps at 5400), **19 source event types** versus the current **11-value synthetic `MatchEventType` enum**, and **0–100-looking coordinates** rather than metres. The existing `SyntheticFixtureGenerator` and `SyntheticMatchService` MUST NOT be advertised as serving this feed. Adapter and API changes need versioned clock/coordinate/event type contracts and regression tests; missing coverage is expressed as unavailable.
